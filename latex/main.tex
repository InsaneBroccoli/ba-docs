Die Messung beruht auf der Injektion eines Chirp-Signals in den zu tunenenden Regelkreisen, um das System über einen breiten Frequenzbereich systematisch anzuregen. Durch Anwendung von Signalverarbeitungstechniken werden die aufgezeichneten Daten ausgewertet. Dadurch können die Übertragungsfunktionen der Regelkreise identifiziert und auf dieser Grundlage geeignete Reglerparameter bestimmt werden, um das Flugverhalten zu verbessern.

Diese Testversuche sollten die Anwendbarkeit, aber auch die Grenzen der Methode für andere Regelkreise aufzeigen. Von der Implementation in Python wurde aufgrund der laufenden Entwicklung der Betaflight-Firmware abgesehen.

Die Ergebnisse dieser Arbeit werden in einem öffentlichen GitHub-Repository veröffentlicht und in einem umfassenden Bericht dokumentiert. Die experimentelle Validierung erfolgt durch reale FPV-Drohnenflüge, um die Wirksamkeit der vorgeschlagenen Methoden zu überprüfen.

\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

This project presents the development of an offline tuning tool for multiple control loops in FPV drones based on the Betaflight firmware. The tool analyzes recorded flight data to estimate the system dynamics, enabling the calculation of optimized controller parameters without the need for iterative flight testing.

The proposed approach is based on the injection of a chirp signal into the control loop, allowing systematic excitation of the system over a wide frequency range. Using signal processing techniques, the recorded data is evaluated to identify the transfer functions of the control loops. Based on these models, suitable controller parameters are derived to improve flight performance.

The tuning algorithms for the angular rate controller and the angle controller are implemented in MATLAB and Python, ensuring accessibility and usability for the FPV community. In addition, prototype implementations for altitude hold and position hold controllers are developed in MATLAB as proof of concept, considering the ongoing development of the Betaflight firmware.

The results of this work are published in a public GitHub repository and documented in a comprehensive report. Experimental validation is performed using real FPV drone flights to verify the effectiveness of the proposed methods.

\chapter{Introduction}
\label{ch:introduction}

First-Person-View (FPV) racing drones require precise and responsive control 
to achieve stable flight behaviour, suppress disturbances such as propeller 
wash and maintain agility during rapid manoeuvres. The flight performance 
strongly depends on the tuning of the flight controller’s feedback loops. 
In particular, the parameters of the angular rate controller determine how 
quickly and accurately the drone reacts to pilot inputs and external disturbances.

In practice, controller tuning is still often performed manually through 
iterative trial-and-error procedures. This requires extensive flight testing 
and considerable piloting experience, making the process time-consuming and 
difficult to reproduce. Although modern flight controller firmware such as 
Betaflight provides extensive configuration options and detailed flight data 
logging, systematic tuning remains a challenge.

One commonly used tool for offline tuning is the PID-Toolbox. In this approach, 
flight logs are recorded during normal flights and later analysed to derive 
suitable controller parameters. However, the system excitation depends entirely 
on the pilot’s inputs and the natural flight behaviour of the drone. As a result, 
not all relevant frequency ranges are sufficiently excited, which can limit the 
quality of the measurements.

In the approach proposed in this thesis, a chirp excitation signal is injected 
directly into the control loop. This allows the system to be excited over a wide 
range of frequencies in a controlled and systematic way, resulting in higher 
quality measurements for system identification and controller tuning.

A previous project introduced a proof-of-concept approach for offline tuning of 
angular rate controllers based on recorded flight data. In the preceding project 
thesis, this concept was restructured and modularized and now serves as the 
foundation for the present work.

The objective of this bachelor thesis is to further refine and extend this 
approach into an offline tuning framework for multiple control loops used in 
Betaflight-based flight controllers. In addition to the existing angular rate 
controller tuner, the framework will be extended with code extensions for tuning 
the angle controller, the altitude hold controller and the position controller. 
This extends the tuning framework beyond the inner rate control loop and enables 
the analysis and tuning of higher-level control layers.

The framework will be implemented primarily in MATLAB and Python and will provide 
tools for analysing flight logs, estimating system dynamics and generating 
controller parameters without requiring repeated flight tests. The software will 
be developed as an open-source library with accompanying documentation for the 
FPV community.

By providing a structured, data-driven approach to controller tuning, this 
project aims to simplify the tuning process and improve flight performance.

\section*{Initial Situation}
\label{sec:IniSituation}

The open-source firmware Betaflight is one of the most widely used platforms for FPV racing drones and is continuously developed by a large community. The quality of the control algorithms is crucial for flight performance, as it determines how quickly and accurately the drone can respond to pilot inputs and external disturbances.

Currently, controller tuning is often performed manually through iterative trial-and-error procedures or with the support of tools such as the PID Toolbox. However, these approaches rely on the natural flight behaviour of the drone and the pilot’s inputs, which may not sufficiently excite all relevant frequency ranges. As a result, this can lead to suboptimal tuning outcomes and requires extensive flight testing as well as significant piloting experience.

During our project thesis, a proof-of-concept approach for offline tuning of the angular rate controller based on recorded flight data, originally developed by Michael Peter, was restructured and modularized. This approach serves as the foundation for the present work and is further refined and extended to include additional control loops.

\section*{Task and Objective}
\label{sec:TaskObjective}

The objective of this bachelor thesis is to further develop and extend the existing offline tuning tool by adding functionality for the tuning of the angle controller. In addition, the tool is to be implemented in Python to improve its accessibility and usability for the FPV community.

Furthermore, proof-of-concept implementations for altitude hold and position hold controllers are developed in MATLAB. These implementations are intended to demonstrate the applicability of the proposed method to additional control loops, while also highlighting its limitations in these contexts.

Due to the ongoing development of the Betaflight firmware, a full Python implementation of these additional controllers is deferred until the firmware has reached a more stable state.

The results of this work are published in a public GitHub repository and documented in a comprehensive report. The overall goal is to provide a structured, data-driven approach to controller tuning that simplifies the process and improves flight performance for FPV drone pilots.

\chapter{Theoretical Foundations}
\label{ch:theory}

This chapter provides the theoretical background for the methods used in this thesis. It covers the fundamental principles of drone dynamics and control, the use of chirp signals for system identification, and the signal processing techniques applied to estimate the transfer functions of the control loops. The concepts introduced here form the basis for the practical implementation and analysis of the control loops in the subsequent chapters.

\section{Drone Types and Sensors}

Unmanned Aerial Vehicles (UAVs) can generally be classified into different categories, such as fixed-wing, rotary-wing, and hybrid systems. This work focuses on multirotor Drones, a subgroup of rotary-wing platforms, which generate lift through multiple rotors.

Among multirotor UAVs, the most common configurations are quadcopters, hexacopters, and octocopters, which differ in the number of rotors (see Fig.~\ref{fig:multirotor_types}). Quadcopters use four rotors and represent the simplest fully controllable multirotor configuration. Due to their comparatively low mechanical complexity, good maneuverability, and widespread use in research and practical applications, they are particularly relevant for modeling and control tasks.

Hexacopters and octocopters extend this concept by using six and eight rotors, respectively. These configurations offer increased thrust, improved fault tolerance, and higher payload capacity, but they also involve greater weight, higher energy consumption, and more complex control allocation.

Since this work is focused with the analysis and modeling of quadcopters, the quadcopter configuration is used as the reference platform throughout the remainder of this chapter.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\linewidth]{Figures/multirotor_types.png}
\caption{Rotary-wing multirotor UAV configurations: quadcopter (left), hexacopter (center), and octocopter (right).}
\label{fig:multirotor_types}
\end{figure}

\subsection*{Sensors}

A quadcopter relies on a variety of sensors to measure its state and environment. The most common sensors include and the most important for this work are:

\begin{itemize}
\item \textbf{Inertial Measurement Unit (IMU):} The IMU consists of accelerometers and gyroscopes that measure linear acceleration and angular velocity. These measurements are used to estimate the drone's orientation and motion.
\item \textbf{Barometer:} A barometer measures atmospheric pressure, which can be used to estimate altitude. This is important for altitude control.
\item \textbf{GPS:} GPS provides position and velocity information and is mainly used for navigation and position control.
\item \textbf{Magnetometer:} A magnetometer measures the Earth's magnetic field and is used to estimate the heading of the drone.
\item \textbf{Electronic Speed Controllers (ESCs):} ESCs control the rotational speed of the motors and provide feedback for motor control.
\end{itemize}

These are the most important sensors for us in this thesis used in a quadcopter. With this sensors we get all the necessary data, which are essential for the offline tuning. However, depending on the application, additional sensors such as cameras or distance sensors can also be used. In practice, the measurements of these sensors are often combined to obtain a more accurate estimate of the drone’s state. These sensor data form the basis for stabilization, navigation, and control.

\section{Drone Dynamics and Control Principles}

A quadcopter is a dynamic system that uses four rotors to generate lift and control its motion. By adjusting the rotational speeds of the individual motors, the drone can control its orientation and movement in three-dimensional space.

Since no direct control surfaces are present, all forces and torques are generated by the propellers. This makes the system inherently unstable and requires continuous feedback control.

In this work, the focus lies on the rotational dynamics of the drone, which are described by the three degrees of freedom: roll, pitch, and yaw. These rotational motions are controlled by varying the thrust of the individual motors.

The following sections introduce the coordinate system, the propeller configuration, and the motor mixing approach, which together form the basis for the control strategy used in this work.

\subsection*{Coordinate System and Rotational Axes}

The dynamics of a quadcopter are typically described using a body-fixed coordinate system, where the axes are defined as follows:

\begin{itemize}
\item The \(x\)-axis points forward, in the direction the drone is facing.
\item The \(y\)-axis points to the right, perpendicular to the \(x\)-axis.
\item The \(z\)-axis points downward, perpendicular to both the \(x\)- and \(y\)-axes.
\end{itemize}

This coordinate system follows the standard aerospace convention and moves together with the drone. All rotational motions are defined with respect to these axes.

The orientation of the quadcopter is described by three rotational degrees of freedom: roll, pitch, and yaw.

\begin{itemize}
\item \textbf{Roll} (\(\phi\)) describes a rotation around the \(x\)-axis. A positive roll angle tilts the drone to the right.
\item \textbf{Pitch} (\(\theta\)) describes a rotation around the \(y\)-axis. A positive pitch angle tilts the drone forward.
\item \textbf{Yaw} (\(\psi\)) describes a rotation around the \(z\)-axis. A positive yaw angle rotates the drone clockwise when viewed from above.
\end{itemize}

The sign conventions for these rotations follow the right-hand rule. This means that if the thumb of the right hand points in the direction of the axis, the curled fingers indicate the direction of positive rotation.

Figure~\ref{fig:body_axes} illustrates the body-fixed coordinate system and the associated rotational axes.

\begin{figure}[h]
\centering
\includegraphics[width=0.45\linewidth]{body_axes.png}
\caption{Body-fixed coordinate system and rotational axes of a quadcopter.}
\label{fig:body_axes}
\end{figure}

All this motion is controlled by adjusting the rotatioal speeds of the four motors, which generate the necessary fources and torques to achieve the desired orientation and movement. The specific configuration of the motors and the resulting control strategy are described in the following sections.

\subsection*{Force and Torque Generation}

As already mentioned, a quadcopter generates all forces and torques through the thrust produced by the propellers. Therefore, the control of the drone is achieved by adjusting the speed of each motor, which in turn changes the thrust and the resulting forces and torques.

To roll the drone is relatively straightforward. This is achieved by increasing the speed of two motors on one side and decreasing the speed of the opposite motors. For example, to roll the drone to the left, the speed of the right motors is increased while the speed of the left motors is decreased. This creates a torque around the \(x\)-axis, causing the drone to tilt to the right, as illustrated in Figure~\ref{fig:roll_pitch}. The same principle also applies to pitch control, where the front and rear motors are adjusted to create a torque around the \(y\)-axis.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.7\textwidth]{Drone_Roll.png}
    \caption{Illustration of roll and pitch control of a quadcopter through differential motor speeds, producing torques about the \(x\)- and \(y\)-axes.}
    \label{fig:roll_pitch}
\end{figure}

To move along the \(x\)- and \(y\)-axes, the drone needs to tilt in the corresponding direction, which is achieved by adjusting the roll and pitch angles. For example, to move forward, the drone pitches forward by increasing the speed of the rear motors and decreasing the speed of the front motors. This creates a horizontal component of the thrust that propels the drone forward. Similarly, to move to the right, the drone rolls to the right by increasing the speed of the left motors and decreasing the speed of the right motors. Therefore, movement in the \(x\)- and \(y\)-directions is indirectly controlled through roll and pitch.

Yaw control is slightly more complex. Since the drone has no direct control surfaces, yaw is achieved by creating a torque around the \(z\)-axis. The propellers of quadcopters do not all rotate in the same direction but instead alternate between clockwise and counterclockwise rotation. As a result, the torque generated by the propellers also alternates in direction. To create a yaw motion, the speed of the motors rotating in one direction is increased, while the speed of the motors rotating in the opposite direction is decreased. This results in a net torque around the \(z\)-axis, causing the drone to rotate in the desired direction, as shown in Figure~\ref{fig:yaw}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.5\textwidth]{Drone_yaw.png}
    \caption{Top view of a quadcopter illustrating yaw control. Increasing the speed of one pair of counter-rotating propellers while decreasing the opposite pair generates a net torque about the \(z\)-axis.}
    \label{fig:yaw}
\end{figure}

If we combine all these control principles, it becomes clear that the drone can perform all maneuvers by adjusting the speeds of the four motors. For this purpose, the software mixes the desired roll, pitch, yaw, and throttle commands into individual motor speed commands. This process is known as motor mixing or control allocation and is a crucial part of the flight controller’s functionality. The simplified motor mixing for a quadcopter can be represented by the following equations:

\begin{align}
M_1 &= T + \phi + \theta - \psi, \\
M_2 &= T - \phi + \theta + \psi, \\
M_3 &= T - \phi - \theta - \psi, \\
M_4 &= T + \phi - \theta + \psi,
\end{align}

where \(M_i\) represents the speed command for the \(i\)-th motor, \(T\) is the throttle command, and \(\phi\), \(\theta\), and \(\psi\) are the desired roll, pitch, and yaw commands, respectively. The specific coefficients in these equations depend on the configuration of the drone and the direction of rotation of the motors.

\section{System Identification Using Chirp Signals}

In this chapter, the theoretical background of the approach used for the estimation and calculation of the different controll loops is described. Since the fundamental approuch of all the control loops is the same, the general approach is described here and the specific details of each control loop are described in the Methodology chapter.

To support the theoretical concepts, a simplified simulation model is added. The simulation is gradually developed throughout this chapter, allowing the reader to follow the modelling process step by step and to better understand the behaviour of the control system. This approach should provide a clear and practical understanding of the control loops and the signal processing techniques used in the estimation and calculation of the control loops.

The detailed application of these principles to the different control loops implemented in Betaflight is discussed in the following chapter.

\subsection*{Chirp Signal}

A chirp signal is a signal in which the frequency increases or decreases over time. It is commonly used in system identification and control engineering to analyze the response of a system over a range of frequencies. \parencite{Matlab_Chirp}

The main advantage of a chirp signal is that it allows a wide frequency range to be excited within a single experiment. Instead of testing individual frequencies one by one, the system is continuously stimulated with increasing frequency. This makes the approach both efficient and well suited for practical applications. \parencite{Matlab_Chirp}

By observing how the system responds to this input, it becomes possible to analyse its frequency-dependent behaviour. In particular, the measured input and output signals can be used to estimate the frequency response and, consequently, the transfer function of the system. This provides valuable insight into the system dynamics and forms the basis for the methods described in the following sections. \parencite{Matlab_Chirp}

\newpage

\subsubsection*{Mathematical Definition}

The instantaneous value of the chirp signal is defined as \parencite{Matlab_Chirp}

\begin{equation}
x(t) = A \cdot \sin(\varphi(t)),
\end{equation}

where \( A \) is the amplitude. The amplitude determines the excitation strength of the signal and therefore influences the signal-to-noise ratio of the measurement.

The phase is defined as \parencite{Matlab_Chirp}

\begin{equation}
\varphi(t) = 2\pi \int_0^t f(\tau)\, d\tau,
\end{equation}

and represents the accumulated instantaneous frequency over time, where \( f(\tau) \) denotes the instantaneous frequency at time \( \tau \). The specific evolution of the frequency over time will be introduced in the following sections.

In practical implementations such as \textbf{Betaflight}, the phase is wrapped once it reaches \( 2\pi \). This keeps the numerical values bounded and results in a sawtooth-shaped wrapped phase signal, which serves as the argument of the sinusoidal excitation.

The behaviour of the chirp signal is determined by several parameters defining the frequency sweep.

For the simulation model introduced in this chapter, the following parameter values are used:

\begin{itemize}
\item \( f_0 \) — starting frequency of the chirp signal (simulation: \( 1\,\text{Hz} \))
\item \( f_1 \) — final frequency of the chirp signal (simulation: \( 600\,\text{Hz} \))
\item \( T \) — total duration of the frequency sweep (simulation: \( 20\,\text{s} \))
\item \( f_s \) — sampling frequency used in the discrete-time simulation (simulation: \( 2000\,\text{Hz} \))
\item \( A \) — amplitude of the chirp signal (simulation: \( 230 \))
\end{itemize}

These parameters are chosen to reflect the typical operating range of the angular rate and the attitude while ensuring that the relevant frequency dynamics are sufficiently excited.

These parameters directly influence the quality of the system excitation and therefore the accuracy of the subsequent frequency response estimation.

\subsubsection*{Common Frequency Profiles}

The chirp signal can be generated using different frequency profiles, which define how the frequency changes over time. The two most common profiles are the linear chirp and the exponential chirp. \parencite{Matlab_Chirp}

\textbf{Linear chirp:}

For a linear chirp, the instantaneous frequency increases linearly over time. \parencite{Matlab_Chirp}

The instantaneous frequency is therefore given by

\begin{equation}
f(t) = f_0 + \frac{f_1 - f_0}{T} \cdot t,
\end{equation}

and the corresponding phase follows by integrating the frequency over time. \parencite{Matlab_Chirp}

\begin{equation}
\varphi(t) = 2\pi\left(f_0 t + \tfrac{1}{2}k t^2\right),
\end{equation}
where \( k = \frac{f_1 - f_0}{T} \) denotes the rate of change of the frequency.

Figure~\ref{fig:linear_chirp} illustrates the resulting chirp signal, the instantaneous frequency \( f(t) \), and the corresponding phase trajectory \( \varphi(t) \) for thesimulation parameters introduced above.

\begin{figure}[h]
\centering
\includegraphics[width=0.95\linewidth]{Figures/linear_chirp.png}
\caption{Linear chirp signal used for the simulation.}
\label{fig:linear_chirp}
\end{figure}

The apparent gaps visible in the chirp signal and in the wrapped phase are not actual
discontinuities. They result from the finite sampling time of the simulation and the limited
resolution of the plotted data.
\newpage

\textbf{Exponential chirp (as used in Betaflight):}

For an exponential chirp, the instantaneous frequency increases exponentially
from the starting frequency \( f_0 \) to the final frequency \( f_1 \) over the time
interval \( T \). This means that lower frequencies are covered more slowly,
while higher frequencies are reached more rapidly. \parencite{Matlab_Chirp}

The instantaneous frequency is defined as

\begin{equation}
f(t) = f_0 \left(\frac{f_1}{f_0}\right)^{t/T}.
\end{equation}

Compared to the linear chirp, this results in a more uniform excitation in logarithmic
frequency space, which is particularly useful when analysing systems using Bode plots. \parencite{Matlab_Chirp}

The corresponding phase trajectory is obtained by integrating the frequency \parencite{Matlab_Chirp}

\begin{equation}
\varphi(t) =
\frac{2\pi T f_0}{\ln(f_1/f_0)}
\left[
\left(\frac{f_1}{f_0}\right)^{t/T}-1
\right].
\end{equation}

These expressions define the phase trajectory \( \varphi(t) \) used both in the simulations and in the time-dependent frequency shifting approach.

The resulting exponential chirp signal, the instantaneous frequency, and the phase trajectory
are illustrated in Figure~\ref{fig:exponential_chirp}.

\begin{figure}[h]
\centering
\includegraphics[width=0.9\linewidth]{Figures/exponential_chirp.png}
\caption{Exponential chirp signal used for the simulation.}
\label{fig:exponential_chirp}
\end{figure}

As with the linear chirp, the apparent gaps in the signal and the wrapped phase are caused by
the discrete sampling time and the limited resolution of the plot.

\subsubsection*{Lag Filter for Chirp Input Shaping}

 In some controll loops, before the chirp signal is injected into the control loop, it is conditioned by a filter to address the differentiating behavior of the controller effort at low frequencies. This differentiating characteristic causes rising gain at low frequencies, which would lead to excessive motor response at the start of the chirp sweep and potentially cause saturation, compromising the quality of system identification data. The filter reduces low-to-mid frequency components of the chirp signal before injection, such that the combined response produces approximately uniform excitation across the frequency range.

The filter is configured with a pole at 3 Hz and a zero at 30 Hz. This configuration corresponds to the transfer function
\begin{equation}
	H(s) = \frac{1 + s/\omega_z}{1 + s/\omega_p}
\end{equation}
where $\omega_z = 2\pi \cdot 30$ rad/s and $\omega_p = 2\pi \cdot 3$ rad/s represent the zero and pole frequencies respectively. The pole introduces the lag component by creating magnitude reduction at frequencies above its cutoff frequency. The zero limits this reduction by introducing magnitude amplification at frequencies above its cutoff frequency. However, since the pole frequency is lower than the zero frequency, the pole's contribution dominates throughout the primary control bandwidth, resulting in a net lag filter. It is important to note that in the Betaflight implementation, the pole frequency ($\omega_p$) must not be set higher than the zero frequency ($\omega_z$), as this would create a lead filter that amplifies high frequencies and could potentially damage the motors.

For the simulation shown in Figure~\ref{fig:chirpleadlag}, the same parameter values introduced in the previous section were used ($f_0 = 1\,\text{Hz}$, $f_1 = 600\,\text{Hz}$, $T = 20\,\text{s}$, $f_s = 2000\,\text{Hz}$). The excitation signal is generated using the exponential chirp formulation described earlier.

\begin{figure}[H]
	\centering

\subsection*{Signal Processing}

To illustrate the influence of the applied signal-processing steps, a simulation is used as a reference. The simulated system represents a simplified model of the plant of the drone's angular-rate controller. It consists of an integrator, a low-pass filter, and a dead-time component. These elements capture the main dynamics of the system and are commonly used in control engineering.

The overall transfer function of the system is given by

\begin{equation}
G(s) = \frac{\omega_1}{s} \cdot \frac{1}{1 + s/\omega_2} \cdot e^{-s/\omega_t}.
\end{equation}

The integrator describes how differences in rotor thrust affect the angular rate over time. The first-order term represents the low-pass behavior introduced by the electronics and actuator dynamics. The dead-time component accounts for delays in the control loop.

For the simulation, the parameters are chosen as

\begin{equation}
\omega_1 = 16 \cdot 2\pi, \qquad
\omega_2 = 13 \cdot 2\pi, \qquad
\omega_t = 60 \cdot 2\pi.
\end{equation}

The structure of the simulation model is illustrated in Figure~\ref{fig:signal_processing_model}.

The chirp signal \( u(t) \) is applied to the system, resulting in the ideal output \( \tilde{y}(t) \).

To emulate realistic measurement conditions, additive disturbance noise \( d(t) \) is superimposed on the output, such that

\subsubsection*{Baseband Filtering via Frequency Rotation}

Measured signals are often affected by noise and unwanted high-frequency components, which can obscure relevant information. This is also the case in the simulated signals considered here, where additive noise is present. To reduce these disturbances while preserving the phase characteristics, a frequency-shifting filtering approach is used \parencite{signal_processing}.

The method shifts the signal to baseband, applies a low-pass filter, and then shifts it back to its original frequency range, enabling focused filtering around the frequency of interest \parencite{signal_processing}.

The underlying principle can be understood using the Fourier shift theorem. Multiplication of a signal $f(t)$ with a complex exponential results in a shift of its spectrum \parencite{signal_processing}

\begin{equation}
e^{i2\pi\xi_0 t} f(t)
\;\Longleftrightarrow\;
\hat{f}(\xi-\xi_0),
\end{equation}

which shifts the spectrum by the frequency $\xi_0$ \parencite{signal_processing}.

In this case, the signal of interest is a chirp signal with a continuously changing instantaneous frequency. Therefore, the frequency shift has to be time-dependent. This is achieved using a complex phasor \parencite{signal_processing}

\begin{equation}
p(t)=e^{i\varphi(t)},
\end{equation}

where \( \varphi(t) \) describes the instantaneous phase of the chirp \parencite{signal_processing}.

Multiplying the measured signal $x(t)$ with this phasor or its complex conjugate results in a rotation of the signal spectrum toward baseband \parencite{signal_processing}

\begin{equation}
y_R(t)=x(t)p(t), \qquad
y_Q(t)=x(t)p^*(t).
\end{equation}

After this rotation, the dominant signal component is centered around $0\,\text{Hz}$, enabling efficient filtering using a low-pass filter \parencite{signal_processing}.

Once the signal has been shifted to baseband, a low-pass filter is applied to remove high-frequency noise components. Since the useful signal is concentrated near zero frequency, the filter can effectively suppress unwanted spectral components outside this region \parencite{signal_processing}.

To avoid phase distortion, forward-backward filtering is employed. This approach applies the filter in both forward and reverse directions, resulting in zero-phase filtering \parencite{signal_processing}.

The filtering operation yields the filtered baseband signals

\begin{equation}
y_R(t) \rightarrow \tilde{y}_R(t), \qquad
y_Q(t) \rightarrow \tilde{y}_Q(t),
\end{equation}

which contain the desired signal components with reduced noise \parencite{signal_processing}.

After filtering, the signal is shifted back to its original frequency range. This is achieved by multiplying the filtered signals with the corresponding inverse phasors and combining the results to obtain a real-valued signal \parencite{signal_processing}

\begin{equation}
x_f(t)
=
\mathrm{Re}
\left(
\frac{1}{2}
\left(
\tilde{y}_R(t)p^*(t)
+
\tilde{y}_Q(t)p(t)
\right)
\right).
\end{equation}

This step reverses the initial frequency rotation and reconstructs a filtered version of the original signal \parencite{signal_processing}.

The filtered signal is then used for further analysis. By reducing the noise before the spectral estimation, the signal-to-noise ratio is improved, leading to more reliable results \parencite{signal_processing}.

The effect of the filtering approach is illustrated in Fig.~\ref{fig:time_filtered}. The upper plot shows the unfiltered signal, where noise becomes dominant at later time instances corresponding to higher chirp frequencies, while the lower plot shows the filtered signal \parencite{signal_processing}.

The method is based on shifting the signal to baseband, applying a low-pass filter, and shifting it back to its original frequency range. A second-order Butterworth low-pass filter with a cutoff frequency of 10 Hz is used. It reduces noise especially at higher frequencies while preserving the main signal characteristics \parencite{signal_processing}.

The filtered signal closely follows the underlying system response. A slight amplitude reduction at higher frequencies can be observed, which is consistent with the low-pass behavior \parencite{signal_processing}.

\subsubsection*{Frequency Response Estimation}

To estimate the transfer function, the relation between input and output signals is analyzed in the frequency domain. For a linear time-invariant (LTI) system, this relation can be written as

\begin{equation}
G(\omega) = \frac{Y(\omega)}{U(\omega)},
\end{equation}

where \(U(\omega)\) and \(Y(\omega)\) denote the Fourier transforms of the input signal \(u(t)\) and the output signal \(y(t)\), respectively \parencite{signal_processing}.

In practice, however, the measured output signal is affected by disturbances. Even after applying the baseband filtering, residual noise remains, especially at higher frequencies. The measured output can therefore be written as

\begin{equation}
Y(\omega) = G(\omega)U(\omega) + D_y(\omega),
\end{equation}

where \(D_y(\omega)\) represents an additive disturbance. A direct estimation by dividing \(Y(\omega)\) by \(U(\omega)\) leads to

\begin{equation}
\frac{Y(\omega)}{U(\omega)} = G(\omega) + \frac{D_y(\omega)}{U(\omega)},
\end{equation}

which shows that the estimate is directly influenced by noise.

To reduce the sensitivity to noise, spectral quantities can be introduced. However, computing these directly from the Fourier transforms leads to the same issues as the direct division \(Y(\omega)/U(\omega)\) \parencite{signal_processing}.

A more robust approach is to estimate the spectral densities using averaging techniques, which reduce the influence of disturbances. This is typically achieved using methods such as Welch’s method, which is described in the following section.

In particular, the estimation becomes unreliable in frequency regions where the input signal is small, since the disturbance term can dominate the ratio.

\newpage

\subsubsection*{Spectral Estimation Using Welch’s Method}

To obtain reliable estimates of the spectral densities, Welch’s method is applied. As discussed in the previous section, direct computation from finite data is sensitive to noise. Therefore, averaging techniques are required to approximate the expected values of the spectral quantities \parencite{System_Identification}.

The spectral densities describe how the signal energy is distributed over frequency and form the basis for estimating the transfer function \parencite{System_Identification}.

Let \(u[n]\) and \(y[n]\) denote the discrete-time input and output signals of length \(N\). In Welch’s method, the signals are divided into \(K\) overlapping segments of length \(L\). Each segment is multiplied by a window function \(w[n]\) to reduce spectral leakage \parencite{System_Identification}.

The \(k\)-th segment of the input signal is given by

\begin{equation}
u_k[n] = u[n + kD]\, w[n], \qquad n = 0, \dots, L-1,
\end{equation}

where \(D\) defines the shift between segments and determines the overlap \parencite{System_Identification}.

For each segment, the discrete Fourier transform (DFT) is computed as

\begin{equation}
U_k(\omega) = \sum_{n=0}^{L-1} u_k[n] e^{-j\omega n}, \qquad
Y_k(\omega) = \sum_{n=0}^{L-1} y_k[n] e^{-j\omega n}.
\end{equation}

To obtain a stable representation in the frequency domain, the squared magnitude of the Fourier transform is used. This corresponds to the signal power and makes the spectral estimate less sensitive to noise \parencite{System_Identification}.

The periodogram estimates are defined as

\begin{equation}
P_{uu,k}(\omega) = \frac{1}{L} |U_k(\omega)|^2, \qquad
P_{yu,k}(\omega) = \frac{1}{L} Y_k(\omega) U_k^*(\omega)
\end{equation}

Welch’s method reduces the variance of the estimates by averaging over all segments. The resulting spectral densities are given by

\begin{equation}
S_{uu}(\omega) = \frac{1}{K} \sum_{k=1}^{K} P_{uu,k}(\omega), \qquad
S_{yu}(\omega) = \frac{1}{K} \sum_{k=1}^{K} P_{yu,k}(\omega), 
\end{equation}

\newpage

Using these quantities, the transfer function estimate is computed as

\begin{equation}
G(\omega) = \frac{S_{yu}(\omega)}{S_{uu}(\omega)}.
\end{equation}

In our example, the spectral densities are estimated using Welch’s method with a segment length of \(L = 4096\) samples and an overlap of 90\%. A Hanning window is applied to each segment to minimize spectral leakage.

The estimated transfer function is shown in Fig.~\ref{fig:transfer_estimation_filtered}. Compared to the direct estimation, a significantly better agreement with the true system response can be observed over a wider frequency range.

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{transferfunction_after_processing.png}
    \caption{Bode plot of the true and estimated transfer function using Welch’s method. The agreement is improved due to the reduced influence of noise.}
    \label{fig:transfer_estimation_filtered}
\end{figure}

To further assess the quality of the estimate, the coherence function is evaluated. The coherence is defined as

$$
\gamma^2(\omega) = \frac{|S_{yu}(\omega)|^2}{S_{uu}(\omega)\, S_{yy}(\omega)},
$$

and takes values in the range \(0 \leq \gamma^2(\omega) \leq 1\). It provides a frequency-dependent measure of how strongly the output is linearly related to the input \parencite{signal_processing}.

The coherence is shown in Fig.~\ref{fig:coherence_estimation}. Values close to one indicate a reliable estimate, whereas lower values indicate that noise or disturbances dominate the measurement.

\end{figure}

\section{Control Loop Calculations}

Although the flight controller consists of several nested control loops, their fundamental
structure is identical. Each loop follows the same basic feedback control principle and differs
mainly in the controlled variable and the chosen controller parameters. Therefore, instead of
analysing every loop individually from the beginning, a simplified model is used to explain the
underlying calculations and controller behaviour.

The simplified control structure used for the analysis consists of a controller \(C\) and a plant \(P\),
which describes the dynamic behaviour of the system being controlled. The reference input \(r\)
is compared with the system output \(y\) to form the control error \(e\). Based on this error, the
controller generates the control signal \(u\), which drives the plant. In addition, the model
considers both input and output disturbances, allowing a more realistic representation of the
system behaviour, as illustrated in Figure~\ref{fig:control_loop_easy}.

Using this simplified model allows the general behaviour of the control loop and the
calculation of the controller terms to be explained in a clear and structured way.
The same principles are later applied to the individual control loops implemented
in the flight controller.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.85\textwidth]{Control_Loop_easy.png}
   \caption{Simplified feedback control loop with controller \(C\) and plant \(P\), including reference \(r\), error \(e\), control signal \(u\), and input/output disturbances.}
    \label{fig:control_loop_easy}
\end{figure}

\subsection*{Calculation of the Control Loop Components}

After the signal processing steps, the control loop components can be calculated.
As in the signal processing stage, the goal is to mitigate the influence of disturbances
and noise on the estimated control loop components. Therefore, only the input signal
of the control loop is used for the estimation.

The advantage of this approach is twofold:
\begin{itemize}
    \item The input signal is not affected by the back-calculation within the control loop and is therefore not influenced by disturbances or noise present inside the loop.
    \item The input signal is not subject to filtering effects, since it is not measured but taken directly from the software. Consequently, it is free from measurement noise and external disturbances.
\end{itemize}

This approach enables a more precise estimation of the transfer function. However,
it also implies that the transfer functions of the individual control loop components
cannot be obtained directly. Instead, they must be derived through mathematical
manipulations.

Consider a simplified control loop consisting of a controller \( C(s) \) and a plant
\( P(s) \), as illustrated in Figure~\ref{fig:control_loop_easy}. The closed-loop
transfer function from the reference input \( R(\omega) \) to the output \( Y(\omega) \) is given by \parencite{lutzTaschenbuchRegelungstechnik}

\begin{equation}
G_{yr}(\omega) = \frac{Y(\omega)}{R(\omega)} =
\frac{C(\omega)P(\omega)}{1 + C(\omega)P(\omega)}.
\label{eq:Gyr}
\end{equation}

The transfer function from the reference input to the controller output \( U(\omega) \)
is

\begin{equation}
G_{ur}(\omega) = \frac{U(\omega)}{R(\omega)} =
\frac{C(\omega)}{1 + C(\omega)P(\omega)}.
\label{eq:Gur}
\end{equation}

By taking the ratio of these two transfer functions, the plant transfer function
can be determined:

\begin{equation}
P(\omega) = \frac{G_{yr}(\omega)}{G_{ur}(\omega)} =
\frac{\dfrac{C(\omega)P(\omega)}{1 + C(\omega)P(\omega)}}
     {\dfrac{C(\omega)}{1 + C(\omega)P(\omega)}} = P(\omega).
\label{eq:Plant}
\end{equation}

To determine the controller, the same principle is applied. The controller transfer
function can be calculated as

\begin{equation}
C(\omega) =
\frac{\dfrac{C(\omega)}{1 + C(\omega)P(\omega)}}
     {1 - \dfrac{C(\omega)P(\omega)}{1 + C(\omega)P(\omega)}}
\end{equation}

These relationships enable the identification of both the plant and the
controller from measurable closed-loop signals. They provide the theoretical
foundation for the analysis of the individual control loops.


\subsection*{Closed-Loop Performance Metrics}

After determining the plant transfer function, the next step is to analyze the behaviour
of the overall system when a controller is applied. This is achieved by evaluating the
closed-loop transfer functions, which describe the system response, disturbance sensitivity,
disturbance rejection capability, and the required controller effort. These measures provide
valuable insights into the stability, robustness, and performance of the controlled system. \parencite{lutzTaschenbuchRegelungstechnik}

The closed-loop transfer function from the reference input to the output is given by \parencite{lutzTaschenbuchRegelungstechnik}

\begin{equation}
G_{yr}(\omega) =
\frac{C(\omega)P(\omega)}
{1 + C(\omega)P(\omega)}.
\end{equation}

The sensitivity function, which describes how sensitive the system output is to
disturbances and model uncertainties, is defined as \parencite{lutzTaschenbuchRegelungstechnik}

\begin{equation}
S(\omega) =
\frac{1}{1 + C(\omega)P(\omega)}.
\end{equation}

The compliance function, representing the system response to disturbances acting
on the plant, is given by \parencite{lutzTaschenbuchRegelungstechnik}

\begin{equation}
SP(\omega) =
P(\omega)\,S(\omega).
\end{equation}

Finally, the controller effort describes the influence of the reference input on the
controller output and is defined as \parencite{lutzTaschenbuchRegelungstechnik}

\begin{equation}
SC(\omega) =
C(\omega)\,S(\omega).
\end{equation}

\subsection*{Compensation of the I-Term}

The integral term of a PI and PID controller is used to compensate for steady-state errors by integrating the control error over time. In flight control systems, this helps to counteract constant disturbances such as motor imbalances or aerodynamic effects. During fast stick movements or aggressive maneuvers, however, the integral term can accumulate too much error \parencite{RT1_Skript}.

In these situations, the accumulated I-term no longer represents a disturbance but instead opposes the intended motion. When the maneuver ends, this can lead to overshoot, bounce-back effects, or slow settling of the system \parencite{RT1_Skript}.

To reduce these effects, Betaflight uses a feature called I-Term Relax \parencite{I_Term}. This mechanism temporarily limits the integration of the I-term when rapid changes are detected. Depending on the configuration, these changes are identified either from the control setpoint or from the measured gyroscope signal. When the detected change exceeds a defined threshold, the I-term integration is reduced or paused.

This allows the controller to respond quickly to fast pilot inputs while preventing excessive buildup of the integral term. During slower movements and steady operation, normal integration is restored. As a result, I-Term Relax improves flight behavior by reducing overshoot and bounce-back while maintaining good disturbance rejection.

For analysis and controller tuning, the effect of I-Term Relax must be considered, as it modifies the controller behavior depending on the current flight conditions.
\begin{figure}[h]
	\centering
	\includegraphics[width=0.8\textwidth]{Control_Loop_Iterm.png}
	\caption{Simplified closed loop system with I-term Relax}
	\label{fig:I_term}
\end{figure}

The measured controller transfer function is compared with an analytically derived controller transfer function. The effect of the I-Term Relax algorithm is therefore included implicitly in the measurement-based result.

To this end, a compensation factor is defined as the ratio between the measured PI controller transfer function and its analytical counterpart:
\begin{equation}
	C_{\mathrm{PI,com}}(\omega) = \frac{C_{\mathrm{PI}}(\omega)}{C_{\mathrm{PI,ana}}(\omega)}
\end{equation}

This frequency-dependent compensation factor represents the combined influence of effects that are not explicitly modeled, including the impact of I-Term Relax. The factor is further applied to both the original analytical PI controller and the newly designed PI controller:
\begin{align}
	C_{\mathrm{PI,ana,new}}(\omega) & = C_{\mathrm{PI,ana}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega) \\
	C_{\mathrm{PI,new,new}}(\omega) & = C_{\mathrm{PI,new}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega)
\end{align}

The resulting compensated controller transfer functions are then reinserted into the closed-loop system for further analysis and evaluation.

\subsection*{Step Response Analysis}

The step response provides a direct and intuitive way to evaluate the performance of a control system. By applying a step input to the reference signal, the resulting output response can be analyzed to assess key performance metrics such as rise time, overshoot, settling time, and steady-state error. These metrics provide insights into the speed, stability, and accuracy of the control system.

Starting from the closed-loop transfer function as seen in Figure~\ref{fig:control_loop_easy}, the system output in the time domain can be obtained by transforming the frequency-domain representation back into the time domain. This relationship is expressed as
\begin{equation}
y(t) = \mathcal{F}^{-1}\left\{ G_{yr}(\omega) \cdot R(\omega) \right\},
\end{equation} 
where \( \mathcal{F}^{-1} \) denotes the inverse Fourier transform, \( G_{yr}(\omega) \) is the closed-loop transfer function from the reference input to the output, and \( R(\omega) \) is the Fourier transform of the step input \parencite{lutzTaschenbuchRegelungstechnik}.

According to the convolution theorem, the system output results from the convolution of the impulse response \( g_{yr}(t) \) with the input signal \( r(t) \). For a step input, the output can be expressed as
\begin{equation}
y(t) = g_{yr}(t) * r(t) = \int_{0}^{t} g_{yr}(\tau) \cdot r(t-\tau) \, d\tau,
\end{equation}
where \( g_{yr}(t) \) is the impulse response of the system, which can be obtained by taking the inverse Fourier transform of the closed-loop transfer function \( G_{yr}(\omega) \) \parencite{lutzTaschenbuchRegelungstechnik}.

Similar to the step response of the system, the step response of the compliance function can be calculated by applying the same procedure to the compliance function \( SP(\omega) \). This allows for a direct comparison of the system response to disturbances with the response to reference inputs.

The step response of the compliance function provides insight into the system's reaction to sudden disturbance forces. While the step response of \( G_{yr} \) evaluates the tracking performance with respect to reference inputs, the compliance step response characterizes the system's disturbance rejection capability and effective stiffness. A small and rapidly settling displacement indicates a stiff and disturbance-resistant system, whereas larger deflections or oscillations suggest higher compliance. Considering both responses therefore enables a more comprehensive assessment of the closed-loop system behavior.

While the step response can be derived analytically from the closed-loop transfer function using the inverse Fourier transform, this approach is not always practical when the system is described by measured or numerically obtained frequency response data. In such cases, the step response is determined directly from the available frequency-domain representation.

In this work, the step response is therefore calculated based on the available frequency response data of the closed-loop system. First, the complex frequency response \( G_{yr}(\omega) \) is limited to a relevant frequency range in order to reduce the influence of high-frequency components. A symmetric spectrum is then constructed to ensure that the resulting time-domain signal is real-valued.

By applying the inverse fast Fourier transform to this spectrum, an approximation of the system's impulse response \( g_{yr}(t) \) is obtained. Since the step response represents the accumulated effect of the impulse response, it is calculated in discrete time as the cumulative sum of the impulse response samples:

\begin{equation}
y[k] = \sum_{i=0}^{k} g[i].
\end{equation}

This approach provides a simple and effective way to estimate the time-domain step response directly from frequency response data \parencite{lutzTaschenbuchRegelungstechnik}.

\section{Theoretical Plant Models}

The goal of this thesis is to analyze the control loops of the Betaflight flight controller based on measurements obtained from flight experiments. To validate the proposed measurement and analysis methods, theoretical plant models are introduced as reference systems.

By comparing the experimentally identified system behavior with these theoretical models, the accuracy and reliability of the applied analysis techniques can be assessed. In addition, the models provide a framework for understanding the interaction between the different control loops implemented in Betaflight.

The following subsections describe the plant models corresponding to the main control layers of the flight controller: angular rate, angle, altitude hold, and position hold.

\subsection*{Motor Dynamics}

As the basis of the overall system, the transfer function of the motor dynamics must be determined.

The motor–propeller system is modeled using the well-established electromechanical model of a DC motor, which can also be applied to brushless DC (BLDC) motors in an equivalent form. The model consists of one electrical and one mechanical differential equation.

The electrical behavior of the motor is described by
\begin{equation}
u(t) = R\,i(t) + L\,\frac{di(t)}{dt} + k_e\,\omega(t),
\label{eq:dc_motor_electrical}
\end{equation}
where $u(t)$ is the applied motor voltage, $i(t)$ the motor current, $R$ the winding resistance, $L$ the inductance, $k_e$ the back electromotive force constant, and $\omega(t)$ the angular velocity.

The mechanical dynamics are given by
\begin{equation}
J_{\mathrm{m}}\,\frac{d\omega(t)}{dt} = k_t\,i(t),
\label{eq:dc_motor_mechanical}
\end{equation}
where $J_{\mathrm{m}}$ is the combined moment of inertia of the motor and propeller, and $k_t$ is the torque constant. For simplicity, viscous friction and aerodynamic load torque are neglected.

Applying the Laplace transform to Eqs.~(\ref{eq:dc_motor_electrical}) and (\ref{eq:dc_motor_mechanical}) and eliminating $i(s)$ yields the transfer function from voltage to angular velocity:
\begin{equation}
G_{\text{motor}}(s) = \frac{\Omega(s)}{U(s)} =
\frac{k_t}{J_{\mathrm{m}} L s^2 + J_{\mathrm{m}} R s + k_t k_e}.
\label{eq:dc_motor_transfer}
\end{equation}

Since the torque constant and the back electromotive force constant have the same numerical value, the transfer function can be simplified to
\begin{equation}
G_{\text{motor}}(s) =
\frac{k}{J_{\mathrm{m}} L s^2 + J_{\mathrm{m}} R s + k^2}.
\end{equation}

This transfer function represents a second-order (PT2) system, capturing both electrical and mechanical dynamics. Due to the small electrical time constant, the inductance mainly affects higher frequencies and can often be neglected. In this case, the motor can be approximated by a first-order (PT1) system, which forms the basis for the subsequent analysis and controller design.

\subsection*{Plant Angular Rate}

The angular rate controller forms the basis of the flight control system, regulating the rotational speed of the drone about its axes. As the innermost control loop, it directly influences the performance of the outer loops, such as the angle and position controllers. Therefore, its plant model serves as the fundamental reference for the overall system analysis.

Based on the motor dynamics described in the previous section, the plant of the angular rate controller can be derived. The input to this plant is the applied motor voltage, while the output is the resulting angular rate.

The transfer function between the input voltage and the motor speed is given by the previously introduced motor model. However, the relationship between motor speed and angular rate is additionally influenced by the drone geometry and the aerodynamic forces generated by the propellers. In particular, variations in motor speed lead to changes in thrust, which ultimately generate the torques responsible for rotational motion. The thrust produced by each propeller can be approximated by

\begin{equation}
T = C_T \rho n^2 D^4,
\end{equation}

where $C_T$ is the thrust coefficient, $\rho$ the air density, $n$ the rotational speed, and $D$ the propeller diameter.

Differential thrust between opposing motors generates a torque that causes the drone to rotate about its axes. The resulting torque is proportional to the thrust difference and the distance from the center of mass to the motor, denoted by $l$, and can be expressed as

\begin{equation}
M_{\text{roll}} = l \cdot \Delta T.
\end{equation}

This expression shows that the generated torque is directly proportional to both the thrust difference and the lever arm, highlighting the importance of the drone geometry for the rotational dynamics.

\begin{equation}
\alpha_{\text{roll}} = \frac{M_{\text{roll}}}{J_{\text{roll}}},
\end{equation}

where $J_{\text{roll}}$ is the moment of inertia about the roll axis. This relation highlights that the rotational dynamics depend both on the generated thrust difference and on the mass distribution of the drone.

Integrating the angular acceleration yields the angular rate. The resulting transfer function is

\begin{equation}
P_{\text{Angular Rate}}(s)
=
\frac{\Omega(s)}{U(s)} =
\frac{k_t}{J_{\mathrm{m}} L s^2 + J_{\mathrm{m}} R s + k_t k_e}
\cdot
\frac{l}{J_{\text{roll}}\,s}.
\end{equation}

This transfer function exhibits an integrator behavior at low frequencies, resulting in a slope of approximately \(-20\,\text{dB/dec}\). At higher frequencies, the motor dynamics introduce additional phase lag and a steeper magnitude roll-off, reflecting the limited bandwidth of the actuator system.

To validate the theoretical model, the frequency response of the plant is estimated from flight data using the previously described identification method. The resulting Bode plot and coherence are shown in Fig.~\ref{fig:plant_gyro_measured}.

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\linewidth]{Plant_Gyro.png}
    \caption{Estimated frequency response of the angular rate plant (roll axis)}
    \label{fig:plant_gyro_measured}
\end{figure}

The estimated response shows good agreement with the expected behavior in the low- to mid-frequency range, exhibiting the characteristic \(-20\,\text{dB/dec}\) slope. This confirms the integrator behavior of the plant.

At higher frequencies, deviations occur due to motor dynamics and unmodeled effects such as aerodynamic disturbances. The coherence remains high over a wide frequency range and decreases at higher frequencies due to measurement noise and reduced signal-to-noise ratio.

\subsection*{Plant Angle}

The angle plant is considerably simpler than the angular rate plant. It is based on the fundamental kinematic relationship between the angular rate and the orientation of the multirotor. The angle corresponds to the time integral of the angular rate, which can be expressed as
\begin{equation}
\theta(t) = \int \omega(t)\, dt.
\end{equation}

Assuming zero initial conditions and applying the Laplace transform, this relationship becomes
\begin{equation}
\Theta(s) = \frac{1}{s}\,\Omega(s).
\end{equation}

This shows that the angle is obtained by integrating the angular rate, corresponding to a multiplication by $\frac{1}{s}$ in the Laplace domain. Consequently, from a theoretical point of view, the angle plant behaves as an ideal integrator with the transfer function
\begin{equation}
P_{\text{Angle}}(s) = \frac{\theta(s)}{\omega(s)} = \frac{1}{s}.
\end{equation}

Through these calculations, we know that we can expect a Bode plot of the angle plant with a slope of -20 dB/decade and a phase shift of -90 degrees, which are characteristic features of an ideal integrator.

To verify this theoretical behavior, the frequency response of the angle plant is estimated from flight data using the system identification approach described earlier. The resulting Bode plot and coherence are shown in Fig.~\ref{fig:plant_angle_measured}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\linewidth]{Bode_Angle.png}
    \caption{Estimated frequency response of the angle plant (roll axis)}
    \label{fig:plant_angle_measured}
\end{figure}

The measured frequency response confirms the expected integrator behavior at low frequencies. In particular, the magnitude exhibits an approximate -20 dB/dec slope, and the phase remains close to -90°, as predicted by the theoretical model.

At higher frequencies, deviations from the ideal integrator behavior can be observed. These effects are mainly caused by measurement noise, limited excitation, and unmodeled dynamics in the system.

The coherence is close to one in the low-frequency range, indicating a reliable estimate. As the frequency increases, the coherence decreases, suggesting that the estimation becomes less reliable due to noise and reduced signal-to-noise ratio.

\subsection*{Plant Position Hold}

The position hold controller includes the angular rate and the angle as inner control loops. Therefore, the plant of the position hold corresponds to the transformation from the drone's attitude (angle) to its position in space. This transformation is determined by the kinematics of the multirotor and the influence of external forces such as gravity.

The position of the drone can be described by its coordinates in three-dimensional space, typically denoted as \( (x, y, z) \). The orientation of the drone influences how the thrust generated by the motors is directed and thus determines its motion in space.

If the drone is hovering at a constant altitude, the total thrust equals the weight of the drone, given by \( mg \), where \( m \) is the mass of the drone and \( g \) is the gravitational acceleration. When the drone tilts by a small angle \( \theta \), a horizontal component of the thrust is generated, leading to a horizontal acceleration, as illustrated in Figure~\ref{fig:drone_pos_hold}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\textwidth]{Drone_Pos_Hold.png}
    \caption{Illustration of a quadcopter tilted by an angle \( \theta \) during position hold. The tilt redirects the thrust vector, generating a horizontal acceleration that results in translational motion.}
    \label{fig:drone_pos_hold}
\end{figure}

The horizontal acceleration can be expressed as
\begin{equation}
a_{\text{hor}}(t) = g \cdot \sin\!\left(\theta(t)\right).
\end{equation}

Assuming that the drone operates at small angles during position hold, the small-angle approximation \( \sin(\theta) \approx \theta \) can be applied. This results in the simplified expression
\begin{equation}
a_{\text{hor}}(t) \approx g \cdot \theta(t).
\end{equation}

By integrating the horizontal acceleration twice with respect to time, the horizontal position of the drone is obtained:
\begin{equation}
x(t) = \int \int a_{\text{hor}}(t) \, dt^2
\approx \int \int g \cdot \theta(t) \, dt^2.
\end{equation}

Applying the Laplace transform yields the transfer function from the tilt angle to the horizontal position:
\begin{equation}
P_{\text{Position}}(s) = \frac{X(s)}{\Theta(s)} = \frac{g}{s^2}.
\end{equation}

This transfer function represents a double integrator. Consequently, the corresponding Bode plot exhibits a magnitude slope of \(-40\,\text{dB/decade}\) and a phase shift of \(-180^\circ\), which are characteristic features of such a system.

\subsection*{Plant Altitude Hold}

The altitude hold directly controls the vertical position of the drone by adjusting the total thrust generated by the motors. Consequently, the plant describes the transformation from motor speed to vertical position.

The altitude plant consists of the motor dynamics and the transformation from motor speed to vertical motion.

The thrust produced by a propeller can be approximated by
\begin{equation}
T = C_T \rho n^2 D^4,
\end{equation}
where \(C_T\) is the thrust coefficient, \(\rho\) the air density, \(n\) the rotational speed, and \(D\) the propeller diameter.

The vertical acceleration follows from the force balance
\begin{equation}
a_{\text{ver}}(t) = \frac{T(t)}{m} - g.
\end{equation}

For hover, the thrust balances the weight of the drone:
\begin{equation}
T_0 = m g .
\end{equation}

The corresponding hover speed is
\begin{equation}
n_0 = \sqrt{\frac{T_0}{C_T \rho D^4}} .
\end{equation}

For small deviations \( \Delta n \) around the operating point \( n_0 \), linearizing the thrust equation yields

\begin{equation}
\Delta T \approx 
\left.\frac{dT}{dn}\right|_{n_0} \Delta n,
\quad \text{with} \quad
\frac{dT}{dn} = 2 C_T \rho D^4 n.
\end{equation}

Substituting \(n_0\) gives
\begin{equation}
\Delta T \approx 
2 C_T \rho D^4
\sqrt{\frac{T_0}{C_T \rho D^4}}
\,\Delta n .
\end{equation}

The corresponding vertical acceleration becomes
\begin{equation}
\Delta a_{\text{ver}}(t)
=
\frac{\Delta T(t)}{m}.
\end{equation}

Applying the Laplace transform and integrating twice yields
\begin{equation}
\Delta S(s)
=
\frac{1}{s^2}
\Delta A_{\text{ver}}(s).
\end{equation}

Thus, the transfer function from motor speed variation to vertical position is
\begin{equation}
\frac{\Delta S(s)}{\Delta N(s)}
=
\frac{2 C_T \rho D^4}{m s^2}
\sqrt{\frac{T_0}{C_T \rho D^4}}.
\end{equation}

Including the motor dynamics, the complete altitude plant becomes
\begin{equation}
P_{\text{Altitude}}(s)
=
\frac{\Delta S(s)}{\Delta U(s)}
=
\frac{2 C_T \rho D^4}{m s^2}
\sqrt{\frac{T_0}{C_T \rho D^4}}
\,P_{\text{Motor}}(s).
\end{equation}

The plant exhibits a double integrator behavior, resulting in a slope of \(-40\,\text{dB/decade}\) at low frequencies, while the motor dynamics introduce additional phase lag at higher frequencies.

To validate the derived model, the frequency response of the altitude plant is estimated from flight data using the previously described identification method. The resulting Bode plot and coherence are shown in Fig.~\ref{fig:plant_altitude_measured}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\linewidth]{Plant_AltHold.png}
    \caption{Estimated frequency response of the altitude plant. Magnitude, phase, and coherence are shown.}
    \label{fig:plant_altitude_measured}
\end{figure}

The estimated frequency response confirms the expected behavior at low frequencies, where the magnitude follows approximately a \(-40\,\text{dB/dec}\) slope, consistent with the double integrator model.

However, the coherence is relatively low in the very low-frequency range due to external disturbances such as wind and slow environmental effects, which reduce the signal-to-noise ratio.

At higher frequencies, the coherence decreases again as measurement noise and unmodeled dynamics become dominant.

\section{Gyro Controller Tuning}

The gyro controller is the innermost control loop of the flight controller and directly regulates the angular velocity of the drone. It is responsible for stabilizing the drone's attitude by adjusting the motor speeds based on the measured angular rates from the gyroscope. Due to its position in the control hierarchy, it operates at a high update rate and reacts quickly to disturbances, thereby ensuring fast and precise stabilization.

The Gyro Controller Tuner was already implemented in the Project Thesis. Therefore, not everything is described in detail again, for example the estimation of the spectra and the spectrograms. However, the main concepts and relevant results are briefly summarized where necessary to ensure a coherent understanding of this work. For more details, please refer to the Project Thesis.

\subsection*{Betaflight Firmware}

During a Betaflight release ..., a new feature was introduced that adds a chirp signal to the system. The main contributor behind this feature was our supervisor Michael Peter. He used this functionality to create a proof of concept for an offline tuning method for the gyro controller. The idea was to use the chirp signal to excite the system and then use the recorded data to estimate the transfer function of the control loop. This approach allows a more accurate analysis of the system dynamics, as the chirp excites the system over a wide frequency range.

Further details about the chirp signal and the underlying theory are described in the theoretical part of this thesis.

\subsubsection*{Acro Mode Control Loop}

In Acro mode, the control loop is designed to directly regulate the angular rates of the drone. The reference input to the controller is the desired angular rate, which is derived from the pilot's stick inputs. The controller then generates the appropriate motor commands to achieve the desired angular rates. The chirp signal is added to the reference input, allowing for the excitation of the system across a wide frequency range. This enables the estimation of the transfer function of the gyro control loop.

The control loop in Acro mode can be represented as follows:

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{Regelkreis_Gyro.png}
    \caption{Control loop structure in Acro mode}
    \label{fig:control_loop_acro}
\end{figure}

Figure~\ref{fig:control_loop_acro} shows the complete gyro control loop in Acro mode. The reference input $w$ (desired angular rate) is combined with a chirp signal to excite the system over a broad frequency range. The resulting signal is fed into a PI controller, which generates the main control action.

After the controller, input disturbances are added before the signal enters the plant $P_{\text{real}}$, representing the real drone dynamics. Output disturbances are introduced after the plant and before the gyro filtering stage. The measured angular rate $y$ is then fed back to the controller.

A key feature of this control structure is the placement of the D-controller in the feedback path instead of the forward path. The derivative action operates on the measured output signal and is fed back negatively. This configuration is used to compensate for a zero in the plant dynamics, improving the system stability while reducing the noise amplification that would occur if the derivative term were applied directly to the reference signal.

Additionally, dedicated filters are used to attenuate high-frequency noise before it affects the control action. This is especially important for the D-controller, since the derivative term is generally very sensitive to noise. Without the D-path filter, measurement noise would strongly affect the D-term and therefore the controller output, which is not desired and could lead to unstable behaviour.

\subsection*{Control Loop Calculation}

Based on the structure of the control loop in Acro mode, the transfer functions of the individual loop components can be estimated from the measured input and output signals. By applying block diagram algebra to the measured data, mathematical models of the plant, controller, and closed-loop behavior can be derived.

As described in the theoretical part of this thesis, the use of block diagram algebra allows the different loop components to be estimated from measurements referenced to the same input signal. This improves the accuracy of the identified transfer functions, since the signals can be filtered more reliably and the influence of feedback effects is reduced. Using the measured frequency responses from the chirp measurements, the dynamic behavior of the different control loop components can then be analyzed separately, enabling a systematic evaluation and tuning of the control system.

\subsubsection*{Estimation of the Closed-Loop Components}

By estimating different transfer functions from the measured data, the behavior of the individual components of the control loop can be analyzed separately. This allows the controller, plant, and feedback paths to be evaluated individually instead of only observing the overall closed-loop response. As already described in the theoretical part, this approach simplifies the system analysis and improves the accuracy of the identified transfer functions.

The first step is to estimate the closed-loop transfer function from the reference input \( r \) to the measured output \( y \), which is denoted as \( G_{yr} \):

\begin{equation}
T_{Gyro}(\omega)=G_{yr}(\omega) = \frac{Y(\omega)}{R(\omega)}
\end{equation}

where \( Y(\omega) \) is the Fourier transform of the measured output signal and \( R(\omega) \) is the Fourier transform of the reference input, including the chirp signal. These signals are filtered and processed as described in the theory chapter in order to reduce noise and improve the quality of the estimated frequency response.

The transfer function \( G_{yr} \) represents the overall closed-loop behavior of the system and can be used to evaluate important characteristics such as bandwidth, phase behavior, and stability margins.

To estimate the plant transfer function, the transfer function from the reference input to the controller output \( u \) is also calculated:

\begin{equation}
G_{ur}(\omega) = \frac{U(\omega)}{R(\omega)}
\end{equation}

where \( U(\omega) \) is the Fourier transform of the controller output signal. This transfer function describes the dynamic relationship between the reference input and the control action applied to the plant.

To estimate the D-term of the controller, the transfer function from the reference input to the signal after the PI controller and the D-path filter is additionally required. This transfer function is denoted as \( G_{vr} \):

\begin{equation}
G_{vr}(\omega) = \frac{V(\omega)}{R(\omega)}
\end{equation}

where \( V(\omega) \) is the Fourier transform of the signal after the PI controller and the D-path filter. This additional transfer function is required because the D-term is implemented in the feedback path of the control loop and therefore cannot directly be separated from the remaining controller dynamics.

With these transfer functions, the plant transfer function can be estimated as

\begin{equation}
G_{\text{Plant}}(\omega) = \frac{G_{yr}(\omega)}{G_{ur}(\omega)}
\end{equation}

In this estimation, the gyro filter is not backcalculated. Therefore, the estimated plant transfer function is divided by the gyro filter transfer function to obtain the real plant dynamics:

\begin{equation}
P_{\text{real}}(\omega) = \frac{G_{\text{Plant}}(\omega)}{G_{\text{FilterGyro}}(\omega)}
\end{equation}

The transfer function of the PI controller can be estimated as

\begin{equation}
C_{\text{PI}}(\omega) = \frac{G_{ur}(\omega)}{1 - G_{yr}(\omega)}
\end{equation}

This estimation is required for the compensation of the I-Term Relax algorithm described in the theory chapter. By comparing the estimated transfer function with the analytical PI controller model, a compensation factor can be calculated and applied to both the original and the newly designed controller.

The D-term and its filter can be estimated in a similar way:

\begin{equation}
C_{\text{D}}(\omega) = \frac{G_{ur}(\omega) - G_{vr}(\omega)}{G_{yr}(\omega)}
\end{equation}

The estimation of the D-term was especially useful during the development of the tuning tool, since it helped to better understand the D-term behavior and identify implementation issues.

\subsubsection*{Implementation of the Tuning Method}

Based on the estimated plant and controller transfer functions, the tuning of the PID controllers can be performed. The goal is to adjust the controller parameters to achieve the desired tuning characteristics, such as stability, responsiveness, and robustness.

The calculation of the tuning parameters for the angular rate control loop follows the same approach as for the angle control loop, but uses different control loop components. The relevant components are the PI controller \(C_{\text{PI}}\), the D-controller \(C_d\), the gyro filter \(G_{\text{FilterGyro}}\), and the estimated plant \(P_{\text{real}}\).

With these components, the transfer functions for the Gang of Four analysis can be calculated. First, the closed-loop transfer function of the angular rate control loop is given by

\begin{equation}
T_{Gyro}(\omega)
=
\frac{
C_{\text{PI}}(\omega)\,
P_{\text{real}}(\omega)\, 
G_{\text{FilterGyro}}(\omega)
}{
1 +
P_{\text{real}}(\omega)
\left(
C_{\text{PI}}(\omega) + C_d(\omega)
\right)
G_{\text{FilterGyro}}(\omega)
}
\end{equation}
The sensitivity function can also be calculated with the new controller as follows. As already discussed in the theoretical part, the sensitivity function is important to evaluate the robustness of the system and the disturbance rejection behavior:

\begin{equation}
S_{Gyro}(\omega)
=
\frac{
1
}{
1 +
P_{\text{real}}(\omega)
\left(
C_{\text{PI}}(\omega) + C_d(\omega)
\right)
G_{\text{FilterGyro}}(\omega)
}
\end{equation}

Or the compliance function, which shows how disturbances acting on the plant affect the system output:

\begin{equation}
SP_{Gyro}(\omega)
=
\frac{
P_{\text{real}}(\omega)
}{
1 +
P_{\text{real}}(\omega)
\left(
C_{\text{PI}}(\omega) + C_d(\omega)
\right)
G_{\text{FilterGyro}}(\omega)
}
\end{equation}

The controller effort can also be calculated with the new controller as follows. This function can be used to evaluate the controller activity and the amplification of noise at higher frequencies:

\begin{equation}
SC_{Gyro}(\omega)
=
\frac{
\left(
C_{\text{PI}}(\omega) + C_d(\omega)
\right)
G_{\text{FilterGyro}}(\omega)
}{
1 +
P_{\text{real}}(\omega)
\left(
C_{\text{PI}}(\omega) + C_d(\omega)
\right)
G_{\text{FilterGyro}}(\omega)
}
\end{equation}

By analyzing these functions, the performance of the new controller can be evaluated in terms of stability, robustness and disturbance rejection. Based on this analysis, further adjustments to the controller parameters can be made iteratively until the desired performance is achieved.

\subsection*{Filter tuning}
Before we start tuning the PID controllers, we need good filtering to have clean signals to work with. The general aim here is to use as little filtering as possible because too much filtering causes delay in the system. However, no quadcopter build is perfect, so at least some filtering is necessary in order to achieve a well-tuned system.

After running the program in MATLAB and importing a log file, you can see in the command window which filter and PID settings were used during that flight. Our tool, in its current state, doesn't copy these values to the code automatically, so the first step is to copy the settings from the command window to the correct position in the code.

We then start by looking at the spectrograms and spectra figures to assess the effectiveness of the current filtering. It is important to note that the spectra and spectrogram plots only show the data recorded in the loaded log file. Changing filter settings in the code does not affect these plots, as they reflect the settings that were active during the flight. To see the effect of any changes, a new flight must be performed and logged with the updated settings.

The \textbf{spectra} in \autoref{fig:Spectra_tuning} shows the frequency composition of the gyro signals.
Peaks in this plot point to vibration sources at specific frequencies.
When we analyze this plot, we look for three main things:
\begin{itemize}
	\item \textbf{Resonance Peaks:} If all three axes show a peak at the same frequency, it usually means there is a resonance in the frame or due to a poorly fixed component. This can be fixed with a specific notch filter or by attaching the loose parts properly.
	\item \textbf{Noise:} A high noise level indicates general vibration issues. By adjusting the D-term low pass filter, you can counteract this. Clean lines in the plot show that the filtering is working well.
	\item \textbf{Axis Sum:} The axis sum shows the overall vibration level across all gyro axes. A properly filtered signal drops quickly after the motor frequencies (after around 600 Hz) and remains low, indicating effective suppression of high-frequency noise and resonances.
\end{itemize}

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{Spectra.png}
	\caption{Frequency spectra of the measured gyro signals}
	\label{fig:Spectra_tuning}
\end{figure}

We can see in this figure that our filter settings work well. The filtered signals have very little noise (smoother lines) and no large resonances. Only the yaw axis has a small peak around 550 Hz, which is acceptable. The axis sum drops nicely and stays low after about 600 Hz, approximately where the motor frequencies end. This shows the drone is running smoothly with vibrations under control. 
The vibrations are also visible in the \textbf{spectrogram} plots in \autoref{fig:Spectrograms_tuning}.
Here, frequencies are plotted against thrust level and the color shows the signal intensity. Red equals much vibration, blue equals little vibration.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{Spectrograms.jpg}
	\caption{Spectrograms}
	\label{fig:Spectrograms_tuning}
\end{figure}

\textbf{Vertical lines} in the spectrogram indicate vibrations at fixed frequencies that do not change with thrust. These usually come from frame resonances or loose components. Such resonances can be removed with static notch filters, but because they are fixed at a single frequency, they must be used carefully. For more robust suppression, especially when frequencies shift due to bent props or changing load conditions, a dynamic notch filter is usually the better choice. Also to mention is, that static notch filters should only be applied, when the same resonances appear in all three axes at the same frequency.

\textbf{Diagonal lines} show vibrations that change with motor speed, such as propeller noise. Using the RPM Filter, these propeller vibrations can be filtered out quite well. This filter uses real-time RPM telemetry data to place notch filters exactly on the fundamental and harmonic frequencies of each motor. As propeller vibrations are directly proportional to motor RPM, this approach eliminates noise at its source instead of relying on fixed or dynamic estimation. In our case, we kept the RPM filter with the default settings. We used \textbf{three-bladed} propellers, so the filter has been set to \textbf{three harmonics}. As we can see in \autoref{fig:Spectrograms_tuning} under the filtered plots, the RPM filter removes the diagonal lines effectively.

\textbf{Aliasing}\\
When sampling a signal that contains frequencies higher than half of your sampling rate, aliasing can occur. This would make high-frequency content appear as lower frequencies, corrupting the measurement data. To avoid this, we applied a PT1 low-pass filter with a cutoff frequency not greater than the sampling frequency divided by two. As we use a 2 kHz logging frequency, we set the cutoff to 800 Hz as a conservative choice.
If aliasing occurs on your drone, it appears in the spectrogram as diagonal lines going down as you move to higher frequencies.

\textbf{Dynamic notch filter}\\
The dynamic notch filter automatically finds and removes mechanical motor noise with the highest amplitude for each axis. The standard setting here is 2 notches from 100 to 600 Hz. Through testing, we found that changing the notch filter count from two to three provided better filtering. We can see in \autoref{fig:Spectrograms_tuning} that the filtered plots don't show any diagonal lines anymore. It is important to keep in mind that adding more notches also adds delay to the system. However, for the robustness of our tune, this trade off can be turned in favor of compensating external influences.

\textbf{D-term low-pass filter}\\
The D-term in a PID controller amplifies high-frequency gyro noise. So this filter controls how much noise is fed back into the control loop. If too much noise passes through, the D-term causes rapid micro-oscillations in the motors, leading to overheating and potential hardware failure.
For our initial flight, we configured a PT3 (third-order) filter with a cutoff of 100 Hz. We chose this filter because PT3 has a much steeper slope than a standard first- or second-order filter. This allows us to aggressively suppress high-frequency noise while minimizing delay in the lower frequencies where the actual flight control happens. The 100 Hz cutoff served as a conservative starting point and worked well. In further tuning, this value can be increased to improve responsiveness while keeping the motors cool. Through trial and error, the value can be increased as long as the motors don't heat up too much during flight.

\textbf{Yaw low-pass filter}\\
The yaw low-pass filter smooths the gyroscope signal by ignoring high-frequency noise. Since the yaw axis typically experiences less mechanical vibration than roll and pitch, the filter can often be configured less aggressively without compromising signal quality.
For our setup, we retained the default Betaflight settings, as they provided good noise suppression without creating unnecessary delay.

Further information about spectra and spectrograms can be found \href{https://github.com/InsaneBroccoli/bf_controller_tuning/blob/main/markdown/Spectrum_Spectrogram}{here}. Also consider looking at the \href{https://www.betaflight.com/docs/wiki/configurator/pid-tuning-tab}{Betaflight wiki page} for more information about Betaflight filters.

\subsection*{Gyro PID Tuning}

To tune the PID controllers, our program provides two different approaches: the step response and the Gang of Four. Both methods are based on the estimated plant and controller transfer functions, allowing for a systematic evaluation of the tuning adjustments. The step response is a time-domain analysis that shows how the system reacts to a sudden change in the reference input, while the Gang of Four is a frequency-domain analysis that provides insights into the stability and robustness of the system across a range of frequencies. For beginners, the step response is often more intuitive and easier to interpret, while the Gang of Four offers a more comprehensive view of the system's behavior, especially for more experienced users.

\subsubsection*{Evaluation Step Response}

The \textbf{step response} plot shows exactly what happens when the pilot moves the stick rapidly. You can see how fast the drone reacts to the command, if it overshoots the target value and how quickly it settles to a steady state. The plot shows three curves, the yellow curve represents the measured response using the active PID values during flight, the blue curve shows the calculated response derived from the plant model and the red curve illustrates the predicted response using the newly tuned PID values implemented in the code.

	\includegraphics[width=0.9\textwidth]{Step_response_pitch_tuned.jpg}
	\caption{Step Response}
	\label{fig:step_response_tuning}
\end{figure}

\begin{itemize}
	\item Tracking (Top Plot): It shows how the drone follows a command.
	\item Compliance (Bottom Plot): It shows how the drone reacts to external disturbances, like wind.

\subsubsection*{Evaluation Gang of Four}

The Gang of Four is a standard set of four transfer functions that together fully characterize a feedback control system. These four plots represent the Sensitivity (S), Complementary Sensitivity (T, Bode plot), Controller Effort (SC) and Compliance (SP). By analyzing these plots, we can assess the stability of the drone, its ability to follow commands, its response to external disturbances and the workload on the motors, all in one comprehensive view.

Figure~\ref{fig:gangoffour_tuning} shows the Gang of Four plots for our tuned system.

\begin{figure}[H]
	\centering
	\includegraphics[width=1.0\textwidth]{gang_of_four_pitch_tuned.jpg}
	\caption{Gang of Four}
	\label{fig:gangoffour_tuning}
\end{figure}

During our tuning process, we found these plots to be invaluable for diagnosing and improving the drone's performance. While all four plots provide useful information, we focused primarily on three of them:
\begin{enumerate}
	\item Sensitivity (S):
	      This plot shows how the system reacts to noise and reference commands. The peak value is a key indicator of stability. In our experience, a peak below 6 dB is ideal for a well-damped system. Higher peaks suggest the drone might oscillate or become unstable, especially during aggressive maneuvers. We noticed that reducing the peak often required balancing stability with responsiveness, as overly conservative settings could make the drone feel sluggish.
	\item Controller Effort (SC):
	      This plot indicates how much work the controller is doing to maintain stability and follow commands. High effort at higher frequencies usually means the system is reacting to sensor noise rather than real disturbances. This can lead to unnecessary motor activity, overheating and wear. During tuning, we found that adjusting the D-term gains and optimizing filters helped reduce high-frequency effort while keeping the drone responsive.
	\item Compliance (SP):
	      Compliance measures how much external disturbances, like wind or propwash, affect the drone's motion. Lower compliance means the drone resists disturbances more effectively. We observed that increasing the P-term gains improved disturbance rejection, but setting them too high caused oscillations during rapid throttle changes. Finding the right balance was critical for maintaining both stability and responsiveness.
\end{enumerate}

In our experience, the Gang of Four plots provided a clear and structured way to assess the impact of tuning changes. Adjustments to the PID gains directly revealed their effects on stability, control effort, and disturbance rejection. This enabled an efficient iterative tuning process and increased confidence in achieving robust performance across varying conditions.

\section{Angle Controller Tuning}

The Betaflight software provides three main flight modes: Angle, Horizon, and Acro.

In Angle mode, the drone’s tilt angle is directly linked to the stick position. The maximum tilt is limited to a predefined value, preventing flips and making this mode particularly suitable for beginners.

In contrast, Acro mode provides full manual control. In this mode, stick inputs define an angular rate rather than a target angle, meaning that the drone continues rotating as long as the stick remains deflected. This allows aggressive maneuvers such as flips and rolls but also requires greater pilot experience.

During this thesis project, an offline tuner for the angular rate controller was further developed to systematically optimize the rate control loop and improveccontroller. As Acro mode performance. The tuner was subsequently extended to also support Angle mode, enabling improved stability and responsiveness while maintaining intuitive handling for beginner pilots.

This extension allows a consistent tuning methodology across different flight modes, improving overall system performance and usability.

\subsection*{Betaflight Firmware}
This chapter describes the implementation of the Betaflight firmware and the modifications required for the proposed offline tuning approach.

The main focus lies on the Angle mode controller. Compared to the standard Acro mode, Angle mode adds an additional outer control loop for attitude stabilization. This results in a cascaded control structure and changes the overall system dynamics compared to the normal rate-controlled flight mode.

In the standard Betaflight implementation, many internal controller signals are not directly accessible through the logging system. However, these signals are required for the offline analysis and transfer function estimation used in this work. Therefore, small modifications were made to the firmware to expose relevant internal controller variables through the existing debug infrastructure.

Additionally, the chirp signal injection used for system excitation had to be adapted for the Angle mode controller. Depending on the injection point of the chirp signal, different parts of the control loop can be analyzed. The implemented modifications therefore also allow the chirp signal to be injected at different positions in the control structure depending on the active flight mode.

The modifications were intentionally kept as small as possible in order to avoid influencing the original flight behavior and the real-time performance of the firmware. The goal was not to redesign the existing controller implementation, but rather to extend the firmware with the functionality required for offline analysis and controller tuning.

\subsubsection*{Angle Mode Control Loop}

In Angle mode, the angular rate controller is extended by an outer angle control loop, resulting in a cascaded control structure.

The stick input initially generates a rate setpoint. Unlike in Acro mode, this rate setpoint is then converted into a target angle. This target angle serves as the reference input for the inner angular rate controller.

The outer angle loop operates at a slower dynamic compared to the inner rate loop. Its task is to generate stable angular rate setpoints that move the drone toward the desired orientation. The inner angular rate controller then reacts much faster and stabilizes the rotational motion of the quadcopter.

The cascaded architecture separates attitude control from angular rate stabilization. While the outer loop ensures convergence toward the desired orientation, the inner loop provides fast dynamic stabilization by regulating the angular velocity. As a result, the system achieves improved disturbance rejection and more intuitive handling characteristics, since the pilot directly commands an angle rather than a rotational rate.

This behavior makes Angle mode especially suitable for beginner pilots and for applications where stable and predictable flight behavior is required. In contrast to Acro mode, the drone automatically returns to the commanded orientation when the stick input is centered.

The Angle mode controller therefore consists of two cascaded loops:
\begin{itemize}
\item The outer angle loop, which computes the angle error.
\item The inner angular rate loop, which computes the rate error.
\end{itemize}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=1.0\textwidth]{Figures/Control_Loop_Angle.png}
    \caption{Cascaded control structure of the Betaflight Angle mode controller.}
    \label{fig:angle_mode_control_loop}
\end{figure}

The angle control loop consists of a proportional controller with an additional feedforward term. Within the offline tuning framework, however, only the proportional controller is optimized.

The feedforward term directly maps the target angle stick input into the control loop. In normal flight operation, this improves the responsiveness of the controller by directly reacting to stick movements.

However, for offline system identification and transfer function estimation, this additional control path complicates the analysis because parts of the controller action no longer originate purely from the feedback control loop.

To simplify the tuning process and focus solely on the proportional controller behavior, the feedforward term is disabled in the modified firmware. This enables a more straightforward analysis of the control loop dynamics without additional influence from the feedforward component.

\subsubsection*{Derivation of the Target Angle}

The target angle is obtained by scaling the commanded angular rate with respect to the maximum achievable rate and the configured maximum tilt angle:

\begin{equation}
\theta_{\text{target}} =
\theta_{\text{limit}}
\cdot
\frac{\omega_{\text{set}}}{\omega_{\text{max}}}
\label{eq:target_angle}
\end{equation}

where

\begin{itemize}
    \item $\theta_{\text{limit}}$ is the maximum allowed tilt angle (e.g., $60^\circ$),
    \item $\omega_{\text{set}}$ is the commanded angular rate derived from the stick input,
    \item $\omega_{\text{max}}$ is the maximum achievable angular rate determined by the rate configuration.
\end{itemize}

This relation ensures a proportional mapping between stick deflection and the resulting target angle.

For example,
\begin{equation}
\omega_{\text{set}} = \omega_{\text{max}}
\Rightarrow
\theta_{\text{target}} = \theta_{\text{limit}}
\label{eq:target_angle_max}
\end{equation}

\begin{equation}
\omega_{\text{set}} = 0
\Rightarrow
\theta_{\text{target}} = 0
\label{eq:target_angle_zero}
\end{equation}

Thus, the stick position scales the target angle continuously within the range
\begin{equation}
-\theta_{\text{limit}}
\le
\theta_{\text{target}}
\le
+\theta_{\text{limit}}.
\label{eq:target_angle_range}
\end{equation}

\subsubsection*{Firmware Modifications}

As already mentioned in the gyro control tuning section, a chirp signal is injected into the control loop to excite the system over a wide frequency range.

If the chirp signal were added in the same way as for the gyro control tuning, it would not be possible to directly calculate the transfer function of the complete system from the target angle to the measured angle. In such a configuration, the chirp signal would be added to the current setpoint and therefore inside the closed control loop. Consequently, the system would have two inputs: the stick input and the injected chirp signal. Additionally, the noise on the signal could not be filtered as described in the theory chapter.

This situation is illustrated in Figure~\ref{fig:angle_mode_control_loop}, which shows the control loop structure currently implemented in the Betaflight firmware.

To overcome this issue, a small modification to the firmware allows the chirp signal to be added directly to the setpoint before it is converted into the target angle. Due to the linear transformation from the rate setpoint to the target angle, the parameters of the chirp signal do not need to be adjusted.

The modified control structure used for the offline tuning framework is illustrated in Figure~\ref{fig:angle_loop_modified}. In this configuration, the chirp signal is injected before the transformation from the rate setpoint to the target angle, allowing the transfer function from the target angle to the measured angle to be estimated directly.

This approach allows the same chirp signal to be used for both modes. As a result, the implementation is simplified and the tuning process becomes more straightforward, since the same excitation signal can be applied without considering structural differences in the control loop.

\subsection*{Control Loop Calculation}

Based on the modified control structure, the dynamic behaviour of the Angle mode control loop can be analysed using the recorded input and output signals. Due to the chirp signal being injected before the transformation to the target angle, the system can be treated as a single-input single-output (SISO) system from the target angle to the measured angle. This allows the same signal processing steps as described in the theory chapter to be applied, including noise filtering and windowing.

\subsubsection*{Estimation of the Closed-Loop Components}

Using the Fourier transforms of the target angle $\Theta_{\text{target}}(\omega)$ and the measured angle $\Theta(\omega)$, the closed-loop transfer function is obtained as

\begin{equation}
G_{cl}(\omega) =
\frac{\Theta(\omega)}{\Theta_{\text{target}}(\omega)}.
\label{eq:G_cl}
\end{equation}

This transfer function describes the complete behaviour of the cascaded control structure, including both the outer angle controller and the inner angular rate controller, as well as the plant dynamics.

As described in the theory chapter, it is also necessary to estimate the transfer function from the target angle to the angular rate $\Omega(\omega)$:

\begin{equation}
G_{wy}(\omega) =
\frac{\Omega(\omega)}{\Theta_{\text{target}}(\omega)}.
\label{eq:G_wy}
\end{equation}

With the two transfer functions $G_{cl}(\omega)$ and $G_{wy}(\omega)$, the plant of the angle control loop can be calculated as follows:

\begin{equation}
G_{\text{plant}}(\omega) =
\frac{G_{cl}(\omega)}{G_{wy}(\omega)}.
\label{eq:G_plant}
\end{equation}

The resulting plant transfer function does not only contain the physical drone dynamics, but also the complete closed-loop behaviour of the inner angular rate controller. From the perspective of the outer angle loop, the stabilized rate controller therefore becomes part of the plant dynamics.

This transfer function forms the foundation for the subsequent tuning of the angle control loop. With the measured plant dynamics, all the necessary information is available to optimize the controller parameters and improve the performance of the Angle mode.

\subsubsection*{Implementation of the Tuning Method}

The calculation of the tuning parameters for the angle control loop follows the same approach as for the angular rate control loop, but uses different control loop components. The relevant components are the gyro control loop \(T_{\text{Gyro}}\), the angle controller and filter \(C_{\text{Angle}}\), and the plant \(P_{\text{Angle}}\).

With these components, the transfer functions for the Gang of Four plot can be calculated. First, the closed-loop transfer function of the angle control loop is

\begin{equation}
T_{Angle}(\omega) =
\frac{C_{\text{Angle}}(\omega)\,T_{\text{Gyro}}(\omega)\,P_{\text{Angle}}(\omega)}
{1 + C_{\text{Angle}}(\omega)\,T_{\text{Gyro}}(\omega)\,P_{\text{Angle}}(\omega)}.
\label{eq:G_cl_new}
\end{equation}

Furthermore, the sensitivity function, which characterizes the disturbance rejection and robustness of the control system, can be expressed as

\begin{equation}
S_{\text{Angle}}(\omega) =
\frac{1}{1 + C_{\text{Angle}}(\omega)\,T_{\text{Gyro}}(\omega)\,P_{\text{Angle}}(\omega)}.
\label{eq:S_new}
\end{equation}

The controller effort can also be calculated. It describes how strongly the controller output reacts to the reference input and is given by

\begin{equation}
SC_{\text{Angle}}(\omega) =
\frac{C_{\text{Angle}}(\omega)}
{1 + C_{\text{Angle}}(\omega)\,T_{\text{Gyro}}(\omega)\,P_{\text{Angle}}(\omega)}.
\label{eq:G_u_new}
\end{equation}

Additionally, the compliance transfer function can be calculated. This transfer function describes how disturbances acting on the plant influence the system output:

\begin{equation}
SP_{\text{Angle}}(\omega) =
\frac{P_{\text{Angle}}(\omega)}
{1 + C_{\text{Angle}}(\omega)\,T_{\text{Gyro}}(\omega)\,P_{\text{Angle}}(\omega)}.
\label{eq:G_c_new}
\end{equation}

These expressions allow the computation of all relevant performance metrics such as gain margin, phase margin, bandwidth, controller effort, disturbance attenuation, and robustness properties. Based on these metrics, plots can be generated and the suitability of the new controller parameters can be systematically evaluated.

\section{Altitude Hold}

The altitude hold control loop maintains a constant altitude by adjusting the throttle based on the measured vertical position. The altitude estimation is mainly based on GPS measurements fused with IMU sensor data to estimate the current vertical position and motion of the drone.

During the development of the tuning tool, major changes were made to the Betaflight firmware affecting the altitude hold functionality and control loop. Therefore, only a proof of concept based on the firmware version from March 2025 was implemented. As a result, the modified firmware will not be merged into the Betaflight codebase, and the tuning tool will not be implemented in Python for community use.

This chapter presents the firmware modifications required for applying the tuning method to the altitude hold controller. It also describes the control loop calculation and the tuning process, including the evaluation of the step response and the Gang of Four. Furthermore, the chapter is intended to support future developers once the ongoing firmware changes are completed and the altitude hold controller has stabilized.


\subsection*{Altitude Hold Control Loop}
In the altitude hold mode, an additional control loop gets activated. It controls the thrust part of the motors as described in the motor mixing chapter. Therefore the drone is able to fly at a constant altitude without the pilot having to adjust the throttle stick. The altitude hold control loop is not cascaded as you can see in the figure \ref{fig:altitude_hold_control_loop}.

Figure \ref{fig:altitude_hold_control_loop} shows the complete altitude control loop in the altitdue hold mode. The reference input w which mostly is zero because the drone set the selected altitude to zero. The resulting signal is fed into a PI controller, which generates the main control action.

The output of the PI controller is then added with a feedback signal in which the D-Term is within. This feedback signal is there to compensate the I-term, which stops the drone form overshooting the target altitude. The resulting signal is then fed into the plant, which consists of the drone dynamics, the motors and the tilt multiplier. The tilt multiplier is a factor that scales the thrust based on the current tilt angle of the drone. This is necessary because the vertical component of the thrust decreases as the drone tilts, and the control loop needs to compensate for this effect to maintain a stable altitude.

In the feedback path which includes the D-term, a D-Boost is implemented. During normal altitude hold operation, a rather small D-term is preferred in order to avoid unnecessary noise amplification and throttle oscillations while maintaining a constant altitude. During fast vertical movements of the drone, however, the D-Boost increases the D-term gain dynamically. This helps to improve the damping and transient behavior of the altitude hold control loop, especially during rapid altitude changes. The D-Boost is calculated based on the estimated vertical velocity. For the measurements performed in this work, the D-Boost was disabled in order to obtain a system behavior which is as linear as possible for the frequency-domain system identification.

\subsection*{Control Loop Calculation}

With the injected chirp signal and the recorded data, the control loop can be calculated. This happens through the same steps as described in the theory chapter, including noise filtering and windowing. The resulting transfer function describes the complete behavior of the altitude hold control loop, including the plant dynamics and the controller. Through some algebraic manipulations, the plant and the controller can be separated, which allows for a systematic tuning of the controller parameters based on the estimated plant dynamics.

\subsubsection*{Estimation of the Closed-Loop Components}
Using the Fourier transforms of the input and output signals, the closed-loop transfer functions can be calculated. The transfer function from the reference input to the output is given by

\begin{equation}
G_{yr}(\omega) = \frac{Y(\omega)}{W(\omega)}
\end{equation}

where \( Y(\omega) \) is the Fourier transform of the measured output signal, \( W(\omega) \) is the Fourier transform of the reference input, including the chirp signal. These signals are getting filtered as described in the theory chapter.

To estimate the plant transfer function, the transfer function from the reference input to the output of the PI controller v is also calculated:

\begin{equation}
G_{vr}(\omega) = \frac{V(\omega)}{W(\omega)}
\end{equation}

where \( V(\omega) \) is the Fourier transform of the controller output signal. 

To complete all the necessary estimations for the tuning process, the transfer function from the reference input to the shared output of the PI controller and the D-term u is calculated as well:

\begin{equation}
G_{ur}(\omega) = \frac{U(\omega)}{W(\omega
])}\end{equation}


With these transfer functions, the plant transfer function can be calculated by rearranging the closed-loop transfer function as follows:

\begin{equation}
G_{Plant}(\omega) = \frac{G_{yr}(\omega)}{G_{vr}(\omega)}
\end{equation}

This approach allows for the identification of the real plant dynamics, which can then be used for further analysis and controller tuning.

The transfer function of the PI controller can be estimated by rearranging the closed-loop transfer function as follows:

\begin{equation}
C_{\text{PI}}(\omega) = \frac{G_{yr}(\omega)}{G_{vr}(\omega) - G_{yr}(\omega)}
\end{equation}

The D term with its filter can be estimated by calculating:

\begin{equation}
C_{\text{D}}(\omega) = \frac{G_{vr}(\omega) - G_{ur}(\omega)}{G_{yr}(\omega)}
\end{equation}

With the estimated plant and controller transfer functions, the complete control loop can be analyzed and the tuning method can be applied to optimize the controller parameters for improved performance.

\subsubsection*{Implementation of the Tuning Method}

The tuning method for the altitude hold control loop is based on the estimated plant and controller transfer functions. \section{Position Hold}

Position Hold is an autonomous control mode that maintains the aircraft at a fixed geographic location and constant altitude without pilot intervention. By combining simultaneous altitude hold and position hold, the system processes real-time GPS position data alongside barometric or GPS altitude measurements. These inputs are used to compute corrective attitude commands that resist external disturbances such as wind and environmental drift. In traditional Angle and Acro modes, a stable hover requires continuous pilot input to compensate for these naturally occurring forces. Position Hold fundamentally eliminates this requirement. When activated, the system establishes a target position based on the current GPS location and aims to maintain the aircraft within 1--2 meters of this reference point by evaluating the position error in both the North-South and East-West axes. These errors are converted into corrective attitude commands through a dedicated position controller. This controller operates as an outer control loop commanding the inner angle controller. Such a hierarchical architecture seamlessly integrates with the existing flight control structure, enabling a consistent application of the tuning methodologies developed for rate and angle control loops.

\textbf{Umrechnung EF in BF und erwähnen, das das auf dem aktuellen stand nicht optimal ist..}

One major aspect of this control strategy is the coordinate transformation. The controller calculates corrective efforts in the Earth-Fixed (EF) frame (North, East, Down) based on GPS data, which must then be mapped into the aircraft's Body Frame (BF) (roll, pitch, yaw) to be executed by the flight controller. Currently, this coordinate transformation is performed after the entire PID calculation, directly rotating the computed attitude commands using the aircraft's instantaneous yaw angle. While functional, applying coordinate rotations on the final PID output rather than mapping the error signals prior to the control loops can lead to suboptimal transient behavior, particularly during rapid heading changes or under severe wind conditions. 

Reliable Position Hold operation depends on a functioning GPS module with a strong satellite fix, providing fundamental position and velocity measurements. A magnetometer (compass) is strongly recommended, as accurate heading estimation directly determines whether corrective attitudes point toward or away from the target location. Without a magnetometer, the system must estimate its heading from the aircraft's flight path. This is achieved by flying a straight-line segment for around 50 to 100 meters at sufficient speed, with a positive pitch angle and zero roll or yaw input. Since the drone is commanded to fly strictly forward, its body-frame forward axis aligns with the direction of motion. By comparing this known thrust direction with the displacement vector derived from GPS over time, the system can resolve the absolute heading of the drone.

Once Position Hold stabilizes, the system maintains altitude using an automatically-adjusted throttle command, while roll and pitch are regulated to zero out position errors.

The position controller employs Proportional (P), Integral (I), Derivative (D), and Acceleration (A) feedback terms to compute corrective attitudes. Tuning these gains determines the aircraft's responsiveness to disturbances, its ability to track the target location, and the control effort required from the attitude controller.

\subsection*{Betaflight Firmware}
In the Betaflight firmware, Position Hold operates asynchronously, executing once per GPS update (typically at 5 to 10 Hz) rather than at the fixed, high-speed rate of the main control loop. The algorithm processes distance and velocity estimates in Earth-fixed coordinates before rotating the computed PID sum into the aircraft's body frame as roll and pitch angle commands. 

Upon receiving new GPS data, the controller first computes the horizontal distance vector from the current aircraft position to the target hold point using spherical trigonometry. This computation runs only when fresh GPS data arrives, effectively reducing computational overhead and exploiting the natural update rate of the GPS unit. The result is a 2D vector with components in the East-West (longitude) and North-South (latitude) directions, expressed in centimeters.

The position controller operates with an intelligent two-phase strategy that distinguishes between the deceleration (stopping) phase and the steady-state (holding) phase. When activated—such as upon mode entry or stick release—the controller enters the \textbf{stopping phase} independently for each axis. Here, the Proportional, Derivative, and Acceleration terms are active, while the Integral term is disabled to prevent windup. Furthermore, the Derivative term is artificially boosted by a factor of 1.6 to ensure rapid deceleration. Once the aircraft's velocity reverses direction on a given axis, which is detected by a sign change between the raw calculated velocity and its low-pass-filtered counterpart, the controller transitions that axis into the \textbf{holding phase}. During the holding phase, the Integral term becomes active to compensate for steady-state disturbances such as wind, while the P and D terms provide stabilization and the Acceleration term contributes feedforward damping.

For each axis, the four feedback terms are computed and summed:

\begin{equation}
u_{\text{axis}} = K_p \cdot d_{\text{axis}} + K_i \cdot \int d_{\text{axis}} \, dt - K_d \cdot v_{\text{filtered}} - K_a \cdot a_{\text{filtered}}
\end{equation}

where $d$ is the position error in centimeters. Velocity is computed numerically as the finite difference of successive position measurements multiplied by the GPS update frequency, then low-pass-filtered using an adaptive first-order (PT1) filter with a cutoff frequency scaled to the current GPS data interval. Acceleration is derived by differentiating the filtered velocity and applying a second layer of low-pass filtering to attenuate high-frequency noise.

After computing the components for both axes, the combined D+A vector magnitude is constrained to a predefined limit (typically 35 degrees) to prevent overly aggressive braking actions during high-speed entries. The total attitude command vector is then limited to the maximum allowed angle (e.g., 50 degrees) by proportional scaling:

\begin{equation}
\text{if} \quad \|\vec{u}\| > \theta_{\max}, \quad
\vec{u} \leftarrow \vec{u} \cdot \frac{\theta_{\max}}{\|\vec{u}\|}
\end{equation}

Because the position controller updates only at the slower GPS frequency while the inner angle controller operates at 100 Hz, a PT3 upsampling filter is utilized. This filter smoothly interpolates the body-frame attitude commands into continuous 100 Hz references, reducing step-change aliasing and minimizing control delays. Finally, a sanity check continuously monitors the distance from the target against a dynamically-scaled threshold based on ground speed. If the aircraft drifts beyond this limit, indicating a GPS anomaly or an extreme disturbance, Position Hold disengages to return manual control to the pilot.

\subsubsection*{Firmware Modifications}
To rigorously evaluate and mathematically tune the Position Hold controller, several custom modifications were implemented within the firmware to facilitate System Identification (SysID) and frequency response analysis. 

The primary addition is the injection of a sinusoidal frequency sweep, or chirp signal, directly into the target position error. By artificially shifting the position setpoint over a predefined frequency range, the drone is forced into a controlled excitation. This allows the tracking performance and disturbance rejection of the position PID to be measured in flight. To ensure the physical system effectively tracks the mathematical chirp, a lead-lag filter (phase compensator) is applied to the chirp excitation, correcting inherent phase delays before the signal is injected into the distance error computation.

For precise measurement repeatability, an automated alignment sequence was introduced prior to the chirp execution. When the chirp mode is activated, a proportional yaw controller automatically rotates the drone to face true North (0 degrees heading). Once the heading error falls within an acceptable tolerance, the alignment is locked, all filters are reset, and the first chirp phase begins on the East-West (longitude) axis. Because the drone faces North, the East-West Earth-Fixed axis cleanly maps to the aircraft's body-frame roll axis. After the first sweep completes the excitation is applied to the North-South (latitude) axis, which corresponds to the aircraft's body-frame pitch axis. This strategic alignment ensures that the Earth-Fixed controller axes and the Body-Frame control axes are perfectly coupled during the system identification flights.

These high-resolution logs are exported into MATLAB, where Welch’s method is utilized to estimate the open and closed-loop transfer functions, enabling precise adjustments to the P, I, D, and A parameters based on empirical flight data.

First, the final software structure and design philosophy are presented, highlighting the object-oriented and modular approach used throughout the project. Subsequently, the selection of Python libraries and the reasoning behind the migration from MATLAB to Python are discussed. Finally, the process of transferring and validating the MATLAB library functions in Python is explained, including the applied testing methodology and the current implementation status.

\subsubsection*{Final Structure Concept}

As already outlined in the project thesis, the tuning tool was implemented using an object-oriented and modular software architecture. This approach enables future extensions of the tool while promoting code reuse across different control loops. Both the MATLAB and Python implementations follow the same structural design in order to ensure consistency between the two environments.

The proof-of-concept implementations for altitude hold and position hold tuning were developed as separate tools without following the same modular architecture. This decision allowed the focus to remain on validating the tuning methodology for these additional control loops without being constrained by the existing software structure. Once the proof of concept is validated, the corresponding implementations can be refactored and integrated into the main modular framework to ensure long-term maintainability and consistency across the entire tuning tool.

Across all controller tuning implementations, the same signal-processing and analysis functions were reused, including functions such as \texttt{apply\_rotfiltfilt} and \texttt{estimate\_frequency\_response}. This ensures a consistent analysis workflow across different control loops while reducing development effort through code reuse.

\subsection*{Conversion from MATLAB to Python}

To make the project more accessible to the FPV community, we decided to migrate the existing MATLAB codebase to Python.
The first step was to select suitable Python libraries that offer similar functionality to MATLAB while maintaining code efficiency and readability.
After evaluating several options, we chose the following libraries:
\begin{itemize}
	\item \textbf{NumPy}: For numerical operations and array manipulations, analogous to MATLAB's matrix operations.
	\item \textbf{SciPy}: For scientific computing tasks, including signal processing functions comparable to MATLAB's capabilities.
	\item \textbf{Matplotlib}: For plotting and visualization, providing features similar to MATLAB's plotting tools.
	\item \textbf{Pandas}: For data manipulation and analysis, useful for handling tabular data as in MATLAB tables.
	\item \textbf{Control Systems Library (control)}: For control system analysis and design, offering functions equivalent to MATLAB's Control System Toolbox.
\end{itemize}
We selected Python version 3.12, as it is well-supported and compatible with the required libraries.
To validate these choices, we developed a prototype script that implements the core functionalities needed for the Drone Tuning Tool.
The script loads flight log data from CSV files, parses and caches the data efficiently and extracts relevant signals such as setpoints and gyro measurements.
NumPy and Pandas are used for numerical and tabular data handling, while SciPy provides signal processing utilities for windowing and frequency analysis.
The Control Systems Library is employed to estimate the system's frequency response and step response from flight data, replicating MATLAB's identification routines.
Matplotlib is used for visualizing raw signals, chirp responses and system characteristics.
The modular structure, including custom data classes and caching, ensures fast and reproducible analysis.
This approach demonstrates that Python and its scientific libraries are suitable replacements for MATLAB in the drone tuning workflow.
While Pandas is not strictly necessary for the prototype, it simplifies data handling and improves code readability.
However, to minimize dependencies and ensure cross-platform compatibility, we may consider removing Pandas in the final implementation.
The flexibility of Python also allows for easier integration with other tools and automation of data processing tasks, which is beneficial for large-scale log analysis.


\subsection*{Transferring the MATLAB Library to Python}

The core functionality of the Drone Tuning Tool resides in its library functions.
To ensure that the Python implementation is both reliable and consistent with the original MATLAB code, we systematically transferred each library function from MATLAB to Python.
For functions with simple numerical outputs, we used \texttt{np.testing.assert\_allclose} with appropriate absolute and relative tolerances, saving the function inputs and outputs from MATLAB and comparing them with the Python implementation.
For more complex functions, such as those involving state-space outputs, we developed dedicated test scripts to compare the behavior of the MATLAB and Python versions across a range of scenarios.

The initial validation process was conducted using flight data from a single test flight.
While several core functions successfully passed the comparison tests with the MATLAB reference implementation, some functions still require further refinement.
Specifically, the functions \texttt{apply\_rotfiltfilt} and \texttt{downsample\_frd} exhibit deviations that exceed the specified tolerance thresholds when compared to their MATLAB counterparts.
Additionally, \texttt{calculate\_transferfunctions} requires revision in the dynamic gyro low-pass filter configuration, as the current implementation produces runtime errors under certain conditions.

For the ongoing development, a comprehensive testing framework is planned that will validate all library functions against flight data from multiple test flights.
This extended validation will provide a more robust assessment of the Python implementation's reliability and help identify edge cases that may not have been apparent in single-flight testing.
The systematic transfer and validation process established so far provides a solid foundation for completing the migration and ensuring consistency between the MATLAB and Python implementations in future work.

\chapter{Discussion}

\section{Discussion Gyro Control Tuning}

The results indicate that the proposed method is capable of predicting the system response with high accuracy when the difference between the baseline and target tuning is moderate. As observed in \autoref{fig:gyro_small_change}, both the transient and steady-state behavior are well captured, suggesting that the identified system model provides a reliable representation of the underlying dynamics in this regime.

However, as the difference between the baseline and target tuning increases, the prediction accuracy decreases. This can be seen in \autoref{fig:gyro_large_change}, where deviations in rise time, overshoot, and damping become more pronounced. This behavior suggests that the system can only be approximated as linear and time-invariant within a limited operating range.

For larger parameter variations, nonlinear effects and time-varying dynamics become more significant, which are not captured by the simplified model used for the prediction. As a result, the calculated step response deviates from the measured response.

Nevertheless, even in these cases, the predicted response still captures the general trend of the system behavior. Therefore, the method remains useful as a qualitative tool for estimating the effect of parameter changes, even when exact quantitative agreement cannot be achieved.

Overall, the results demonstrate that the accuracy of the proposed tuning approach strongly depends on the similarity between the baseline and target configurations. This highlights the importance of selecting appropriate baseline data for reliable system identification and controller tuning.

\section{Discussion Angle Control Tuning}

The results demonstrate that the proposed tuning tool is capable of accurately predicting the system response for moderate parameter changes. As shown in \autoref{fig:step_response_angle_tuning}, the estimated and measured step responses are in close agreement, indicating that the identified plant and controller models provide a reliable representation of the system dynamics in this operating range.

In addition, the updated tuning leads to an improved dynamic performance compared to the baseline configuration. The faster response combined with a well-damped behavior suggests that the tuning tool can be effectively used to enhance the control performance of the drone.

However, the accuracy of the estimation decreases for larger changes in the controller gains. This can be observed in \autoref{fig:step_response_large_gain_difference}, where the deviation between the estimated and measured responses becomes more pronounced. This behavior indicates that the underlying assumption of a linear and time-invariant system is only valid within a limited parameter range.

For larger gain differences, nonlinear effects and time-varying dynamics become more significant and are not fully captured by the model used for prediction. As a result, the estimation accuracy decreases.

Nevertheless, even in these cases, the estimated response still captures the general trend of the system behavior. Therefore, the tuning tool remains useful as a qualitative method for predicting the impact of parameter changes.

Overall, the results highlight that the reliability of the proposed tuning approach depends on the magnitude of the parameter variation. For best results, the tool should be applied within a moderate range of tuning adjustments.

\textbf{Title}

Betaflight -- Offline Controller Tuning

\vspace{0.5em}

\textbf{Description}

Betaflight is an open-source project specialized in the control of FPV quadcopters,
particularly in the field of racing drones. The firmware is continuously developed by a
large community and is available on many different hardware platforms. Betaflight is the
most widely used firmware for FPV drones and is used by both hobbyists and professional
pilots.

Flight performance strongly depends on the quality of the rate control system. The
controllers are responsible for stabilizing the drone, suppressing disturbances such as
wind and prop wash, and ensuring agile responses to pilot inputs. Therefore, the
controllers and filters must be carefully tuned and configured to achieve optimal flight
performance. FPV pilots typically fly in ACRO mode, meaning that the system is rate
controlled and the pilot stick inputs are interpreted as setpoints for the rate controller.

Within the FPV community, controller tuning is commonly performed using a trial-and-error
approach. Pilots iteratively adjust controller parameters and test the resulting flight
behaviour. This process can be time-consuming and frustrating, especially for beginners,
as finding suitable controller parameters is often difficult.

A proof of concept already exists which enables offline tuning of the rate controllers
based on a measurement-derived drone model obtained from chirp signal experiments during
flight. The objective of this project is to further develop this offline tuning method for
the gyro rate controllers.

The goal is to develop a complete, cleanly implemented, and easily extendable open-source
library in both MATLAB and Python. In addition, comprehensive documentation with practical
examples shall be created for the Python implementation using GitHub Markdown
documentation. The long-term objective is to provide a library that can be used by the FPV
community to improve drone flight performance and simplify the controller tuning process.
